How it works

TL;DR We send bug reports, not patches. Any patch attached is AI-generated and has only passed an A/B test. No human has reviewed it.

Purpose

We want the Linux kernel to be more secure. We find bugs much faster than we can patch them, so we report them the way syzbot does, to ask the community for help. We respect everyone's time. We also make mistakes, and suggestions and complaints are welcome (cedalion@bugs.sh).

We ask nothing of you. A Reported-by: tag if you fix the bug lets us close it on our side. Tell us if a report is wrong, a duplicate or already fixed. If you would rather not receive these, for one subsystem or at all, say so and we stop.

Verified

Bug

The PoC triggers the sanitizer report we quote, in the environment the report gives you: kernel commit, config and QEMU boot script. We ran it that way. If it does not reproduce for you, that is our bug and we want to hear about it. Race conditions are the exception: they may need several runs.

Patch

If a patch is attached, its A/B test is real: we built both kernels and ran the same PoC, and it crashes without the patch and runs clean with it. That does not make the patch ready to apply to the kernel. The reasons are in the next section.

Not verified

Patch

The patch in a report is written by an LLM, and a passing A/B test does not make it ready to merge. It can still:

  • process the data in a way the subsystem never intended
  • suppress the crash without fixing the root cause
  • fail in ways only a reviewer would catch
  • break functionality or hurt performance
  • introduce new bugs
  • …

So the patch carries no Signed-off-by, is not posted to any list, and nobody is asked to review it. The root-cause analysis in the report is machine-generated and sits in the same category. Do not trust either of them as ground truth.

Duplicates

Before sending we search lore and recent patches, and do our best to make sure a report is not a duplicate of a known bug. That check is not complete: two reports can share one root cause and look nothing alike, and root-cause analysis is still a hard problem. If a report duplicates something already known, replying with #co dup: <lore link> closes it on our side.
