Patch

Warning Do NOT send an AI-generated patch without reviewing and validating it yourself.

This page is a guide to using bugs.sh artifacts to reproduce a bug, test the provided patch or develop a better one, and send it to the appropriate maintainers.

Human review

We provide AI-generated patches that pass an A/B test against the PoC, but AI makes mistakes: a patch can suppress the crash without fixing the root cause, violate subsystem design, break functionality, or introduce new bugs. Treat it as a starting point, not a ready-to-send fix. Sending an unverified patch would waste maintainers’ time and burden the review process.

We share the reproduction artifacts so contributors can verify our patch or develop a better one. To keep disclosure ethical, every public bug is low severity or already patched. Most are security issues; when a fix is merged, we request a CVE where applicable, and the contributor receives credit for the work.

Open issues

bugs.sh has three views: Patched, Processing and Vulnerable. Processing lists open issues; it means the bug report has been sent, and your contribution can help a patch land sooner. Each issue links to its initial report on lore and to a search for related patches. Check that search before starting. If a patch has already been posted, join the discussion and help improve it, or, preferably, choose another issue that does not yet have a patch.

Reproduction

Our storage is limited, so we cannot provide a compiled Linux kernel for every issue. Instead, bugs.sh provides the metadata and scripts needed to build the affected Linux kernel and trigger the bug.

A bug could have been fixed by a commit that bugs.sh has not detected; developing another patch would duplicate that work. Maintainers apply fixes through the subsystem’s source-code-management (SCM) tree. Reproduce the bug on the current tip of that tree before developing a patch. If it no longer reproduces, inspect the intervening commits instead of preparing a duplicate fix.

The Linux kernel records subsystem ownership and source trees in MAINTAINERS. From an existing Linux kernel source checkout, get_maintainer.pl --scm reads those entries for the affected file and reports the tree used by its maintainers: 

./scripts/get_maintainer.pl --scm -f <path/to/affected/file>

Pass the reported SCM URL to repro.sh --tree. For bug ID 4bda3bf8e1a2b780, the networking SCM tree is: 

git://git.kernel.org/pub/scm/linux/kernel/git/netdev/net.git
export BUG_ID=4bda3bf8e1a2b780
export KERNEL_TREE=git://git.kernel.org/pub/scm/linux/kernel/git/netdev/net.git
./reproduction/repro.sh build "$BUG_ID" --latest --host \
  --tree "$KERNEL_TREE"
./reproduction/repro.sh run   "$BUG_ID" --latest --host \
  --tree "$KERNEL_TREE"

--host keeps the Linux kernel source and build output in ./4bda3bf8e1a2b780-net-latest/, making it easy to inspect and edit the source. The script checks out the current tip of the selected tree, applies the provided configuration, compiles it, boots it with QEMU and runs the PoC.

Docker mode is also available: omit --host. To reproduce the bug on the older Linux kernel version where we originally triggered it, omit --latest; the script then checks out the recorded commit.

Patch

After confirming that the bug still reproduces, read the report, inspect the affected code and confirm the root cause. Continue working in the SCM tree built above, then fetch the bugs.sh patch. The published patch is AI-generated and is only a starting point: inspect it carefully, apply it if useful, or replace it with your own fix. 

export BUG_ID=4bda3bf8e1a2b780
export KERNEL_TREE=git://git.kernel.org/pub/scm/linux/kernel/git/netdev/net.git
export PATCH_URL="https://bugs.sh/b/${BUG_ID}/patch.diff"
pushd "${BUG_ID}-net-latest/linux"
wget -O ../patch.diff "$PATCH_URL"
git apply ../patch.diff

Inspect and edit the applied patch in the source tree. When it is ready to test, return to the Cedalion checkout, rebuild the same tree, and run the reproducer: 

popd
./reproduction/repro.sh build "$BUG_ID" --latest --host --force \
  --tree "$KERNEL_TREE"
./reproduction/repro.sh run   "$BUG_ID" --latest --host \
  --tree "$KERNEL_TREE"

A good patch fixes the root cause without changing the subsystem’s intended behavior. Review the final diff, run the relevant subsystem tests, and add these trailers to the commit message: 

Reported-by: co+<BUG_ID>@bugs.sh
Closes: <URL of the initial report on lore>

Reported-by: credits our work finding the vulnerability and lets bugs.sh track the fix. Closes: connects the patch to the original report.

Commit message

Follow the Linux kernel’s Submitting patches guide. Explain the problem, confirm its root cause and describe why the change fixes it. Include a short decoded crash excerpt. You can copy one from the bugs.sh report or decode your reproduction log from the Linux kernel source tree: 

export BUG_ID=4bda3bf8e1a2b780
pushd "${BUG_ID}-net-latest/linux"
./scripts/decode_stacktrace.sh vmlinux < ../repro.log
popd

A typical commit message has this shape:

<subsystem>: <short imperative summary>

<Describe the failure and its impact.>

<Explain the root cause and why this change fixes it.>

<Short decoded crash excerpt.>

Reported-by: co+4bda3bf8e1a2b780@bugs.sh
Closes: <URL of the initial report on lore>
Fixes: <introducing-commit> ("introducing commit subject")
Signed-off-by: Your Real Name <you@example.com>

Fixes: identifies the commit that introduced the bug. Follow Reported-by: with the initial lore report URL in Closes:. Signed-off-by: must use your real name and email address.

Send the patch

Commit the tested change with your sign-off, generate the email patch, check it against the Linux kernel style rules, and use the Linux kernel source tree to identify the appropriate maintainers and mailing lists: 

export BUG_ID=4bda3bf8e1a2b780
pushd "${BUG_ID}-net-latest/linux"
git add <changed-files>
git commit -s
git format-patch -1 --stdout > "../${BUG_ID}.patch"
./scripts/checkpatch.pl --strict --show-types "../${BUG_ID}.patch"
./scripts/get_maintainer.pl "../${BUG_ID}.patch"

Resolve relevant checkpatch.pl findings, then use the maintainers and lists reported by get_maintainer.pl as the recipients. Check the subsystem’s maintainer handbook for any additional rules before sending: 

git send-email --to="<maintainer-or-list>" \
  --cc="<list-or-reviewer>" "../${BUG_ID}.patch"
popd

Community

Linux kernel development is a community process. Follow the Linux kernel guides and each subsystem’s expectations, and listen carefully to review feedback. We have learned a great deal from maintainers and contributors, who have been generous with their time and guidance.

We follow discussions that include us and can help reproduce the issue, test revisions and work with contributors to help the patch land.

Our goal is not a larger CVE count. It is a more secure Linux kernel. Please do not treat LLM-generated patches as a shortcut or send them without understanding, reviewing and testing them yourself.
