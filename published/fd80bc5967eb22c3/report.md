# xhci: slab out-of-bounds write in `xhci_align_td()`

|  |  |
|---|---|
| Bug class | out-of-bounds write (slab) |
| Subsystem | drivers/usb/host (xHCI) |
| Location | `drivers/usb/host/xhci-ring.c` (`xhci_align_td()`, inlined into `xhci_queue_bulk_tx()`) |

## Root cause

`xhci_endpoint_init()` reads the raw value and then normalizes it in place, precisely because devices are known to lie:

```c
/* drivers/usb/host/xhci-mem.c:1465, 1474-1489 */
	max_packet = xhci_usb_endpoint_maxp(udev, ep);
	...
	/* HS bulk max packet should be 512, FS bulk supports 8, 16, 32 or 64 */
	if (usb_endpoint_xfer_bulk(&ep->desc)) {
		if (udev->speed == USB_SPEED_HIGH)
			max_packet = 512;
		if (udev->speed == USB_SPEED_FULL) {
			max_packet = rounddown_pow_of_two(max_packet);
			max_packet = clamp_val(max_packet, 8, 64);
		}
	}
	/* Set up the endpoint ring */
	virt_dev->eps[ep_index].new_ring =
		xhci_ring_alloc(xhci, 2, ring_type, max_packet, mem_flags);
```

That normalized value becomes the ring's recorded buffer length and the actual allocation size:

```c
/* drivers/usb/host/xhci-mem.c:382 */
	ring->bounce_buf_len = max_packet;
/* drivers/usb/host/xhci-mem.c:335, 344 → xhci_segment_alloc() → xhci-mem.c:48-52 */
	if (max_packet) {
		seg->bounce_buf = kzalloc_node(max_packet, flags, dev_to_node(dev));
```

`xhci_align_td()` — the only writer of that buffer — ignores `ring->bounce_buf_len` entirely and re-derives from the descriptor:

```c
/* drivers/usb/host/xhci-ring.c:3550, 3573-3586 */
	max_pkt = xhci_usb_endpoint_maxp(urb->dev, urb->ep);   /* RAW, unnormalized */
	...
	new_buff_len = max_pkt - (enqd_len % max_pkt);

	if (new_buff_len > (urb->transfer_buffer_length - enqd_len))
		new_buff_len = (urb->transfer_buffer_length - enqd_len);

	if (usb_urb_dir_out(urb)) {
		if (urb->num_sgs) {
			len = sg_pcopy_to_buffer(urb->sg, urb->num_sgs,
						 seg->bounce_buf, new_buff_len, enqd_len);
		} else {
			memcpy(seg->bounce_buf, urb->transfer_buffer + enqd_len, new_buff_len);
		}
		seg->bounce_dma = dma_map_single(dev, seg->bounce_buf, max_pkt, DMA_TO_DEVICE);
```

`new_buff_len` is clamped **only** against the remaining URB length — never against the size of `seg->bounce_buf`. `xhci_usb_endpoint_maxp()` (`drivers/usb/host/xhci.c:2949-2955`) applies no clamping of its own; it returns `usb_endpoint_maxp(&host_ep->desc)` (or the eUSB2 companion field) verbatim.

**The divergence is device-controlled and explicitly tolerated by the USB core.** `usb_parse_endpoint()` clamps `wMaxPacketSize` only against `high_speed_maxpacket_maxes[]`, whose bulk entry is **1024**, with the comment saying so outright:

```c
/* drivers/usb/core/config.c:223-229 */
static const unsigned short high_speed_maxpacket_maxes[4] = {
	[USB_ENDPOINT_XFER_CONTROL] = 64,
	[USB_ENDPOINT_XFER_ISOC] = 1024,

	/* Bulk should be 512, but some devices use 1024: we will warn below */
	[USB_ENDPOINT_XFER_BULK] = 1024,
	[USB_ENDPOINT_XFER_INT] = 1024,
};
```

and the follow-up check for HS bulk emits only a `dev_notice`, deliberately leaving the descriptor unmodified:

```c
/* drivers/usb/core/config.c:501-508 */
	if (udev->speed == USB_SPEED_HIGH && usb_endpoint_xfer_bulk(d)) {
		if (maxp != 512)
			dev_notice(ddev, "config %d interface %d altsetting %d "
				"bulk endpoint 0x%X has invalid maxpacket %d\n", ...);
	}
```

So the two concrete divergences are:

- **High-speed bulk, `wMaxPacketSize = 1024`**: allocation = 512 bytes (`max_packet` forced to 512), copy length up to 1024 → **512-byte slab out-of-bounds write** (kmalloc-512).
- **Full-speed bulk, `wMaxPacketSize = 63`** (≤ 64, so untouched by the core): allocation = `clamp_val(rounddown_pow_of_two(63), 8, 64)` = 32 bytes, copy length up to 63 → **31-byte out-of-bounds write**.

**Secondary consequences of the same mismatch.** `dma_map_single(dev, seg->bounce_buf, max_pkt, ...)` maps the *raw* length while `xhci_unmap_td_bounce_buffer()` unmaps `ring->bounce_buf_len` (`xhci-ring.c:857, 862`) — an asymmetric map/unmap. On the IN direction the controller is handed a mapping of `max_pkt` bytes over a smaller buffer (device-driven DMA overflow), and the copy-back at `xhci-ring.c:872-873` does `memcpy(urb->transfer_buffer + seg->bounce_offs, seg->bounce_buf, seg->bounce_len)` with `seg->bounce_len == new_buff_len`, reading past the allocation.

**Why it is NOT already fixed.** I grepped every occurrence of `bounce_buf`, `bounce_buf_len` and `bounce_len` in `xhci-ring.c`, `xhci-mem.c` and `xhci.h`: `ring->bounce_buf_len` is referenced **only** by the two `dma_unmap_single()` calls at `xhci-ring.c:857` and `:862`. It is never consulted in `xhci_align_td()`, so no clamp exists anywhere on the write path. The normalization lives solely inside `xhci_endpoint_init()`. Notably the *stream* ring path is self-consistent — `xhci.c:3693` passes the raw `usb_endpoint_maxp(&eps[i]->desc)` to `xhci_alloc_stream_info()`, so allocator and consumer agree there — which is exactly why only the non-stream bulk ring from `xhci_endpoint_init()` disagrees with its consumer.

## Trigger

1. Build or emulate a USB device (a Facedancer/Raspberry Pi gadget, or `dummy_hcd`/`raw-gadget` for software testing) that enumerates at **high speed** and declares a **bulk** endpoint with `wMaxPacketSize = 1024`.
2. Plug it into an xHCI host. `usb_parse_endpoint()` accepts the descriptor (1024 ≤ the 1024 bulk max) and only logs `bulk endpoint 0x81 has invalid maxpacket 1024`; the descriptor keeps the value 1024.
3. `xhci_endpoint_init()` forces `max_packet = 512` for the ring, so every segment's `bounce_buf` is a 512-byte `kzalloc`.
4. Drive bulk OUT traffic that exercises the bounce path: `xhci_align_td()` runs from `xhci_queue_bulk_tx()` when a multi-TRB TD's non-final TRB lands on the last usable TRB of a ring segment (`trb_is_link(ring->enqueue + 1)`) and `*trb_buff_len <= unalign`. Scatter-gather URBs with sub-1024-byte segments (via usbfs or usb-storage) reach it readily.
5. With `enqd_len % 1024 < 512` and at least that much URB data remaining, `new_buff_len = 1024 - (enqd_len % 1024)` exceeds 512, and the `memcpy`/`sg_pcopy_to_buffer` at `xhci-ring.c:3581/3586` writes past the 512-byte allocation. KASAN reports a slab-out-of-bounds write; without KASAN this corrupts the adjacent kmalloc-512 object.

The full-speed variant (`wMaxPacketSize = 63`) is easier to reach in some respects — the 32-byte buffer is exceeded by any `new_buff_len > 32` — but corrupts less.
