# xfs: slab out-of-bounds read in xlog_recover_buf_reorder()

|  |  |
|---|---|
| Bug class | Slab out-of-bounds read |
| Subsystem | fs/xfs |
| Location | `fs/xfs/xfs_buf_item_recover.c`:162 (`xlog_recover_buf_reorder()`) |

## Root cause

XFS log recovery `xlog_recover_buf_reorder()` reads `blf_flags` before any
length validation of region 0.

`xfs_buf_log_check_iovec()` is the function that validates the length of a
buffer log item's region 0. It has exactly one caller —
`xlog_recover_buf_commit_pass1()`:

```c
static int
xlog_recover_buf_commit_pass1(
	struct xlog			*log,
	struct xlog_recover_item	*item)
{
	struct xfs_buf_log_format	*bf = item->ri_buf[0].iov_base;

	if (!xfs_buf_log_check_iovec(&item->ri_buf[0])) {
		xfs_err(log->l_mp, "bad buffer log item size (%zd)",
				item->ri_buf[0].iov_len);
		return -EFSCORRUPTED;
	}
```

But `->reorder` runs **before** `->commit_pass1` for the same item:
`xlog_recover_commit_trans()` calls `xlog_recover_reorder_trans()` first
(`fs/xfs/xfs_log_recover.c`:2042), and only afterwards walks the reordered list
invoking `commit_pass1`. And `xlog_recover_buf_reorder()` dereferences region 0
with no length check at all:

```c
STATIC enum xlog_recover_reorder
xlog_recover_buf_reorder(
	struct xlog_recover_item	*item)
{
	struct xfs_buf_log_format	*buf_f = item->ri_buf[0].iov_base;

	if (buf_f->blf_flags & XFS_BLF_CANCEL)
		return XLOG_REORDER_CANCEL_LIST;
	if (buf_f->blf_flags & XFS_BLF_INODE_BUF)
		return XLOG_REORDER_INODE_BUFFER_LIST;
	return XLOG_REORDER_BUFFER_LIST;
}
```

`blf_flags` is a `unsigned short` at **offset 4** of `struct
xfs_buf_log_format`. A region 0 of only 4 bytes — the minimum that survives
`xlog_recover_add_to_trans()`, which needs `blf_type` at offset 0-1 and
`blf_size` at offset 2-3 — makes this a 2-byte read past a `xlog_kvmalloc(4)`
object, i.e. a KASAN slab-out-of-bounds on kmalloc-8.

`xlog_recover_buf_ra_pass2()` (line 176) is worse in reach: it reads
`blf_blkno` at offset **8** and `blf_len` at offset 6, up to 10 bytes past a
4-byte region, and feeds them to `xlog_buf_readahead()`. It is not reached on
the shortest path: PASS1 aborts with `-EFSCORRUPTED` from
`xlog_recover_buf_commit_pass1()` before PASS2 ever starts, so the `reorder`
callback is the reachable instance of the pattern. `ra_pass2` would be reached
with a region 0 that is long enough to pass `xfs_buf_log_check_iovec()` but
still shorter than `blf_blkno`'s extent.

```c
	/* xlog_recover_reorder_trans(), fs/xfs/xfs_log_recover.c ~1907-1926 */
	list_for_each_entry_safe(item, n, &sort_list, ri_list) {
		enum xlog_recover_reorder	fate = XLOG_REORDER_ITEM_LIST;

		/* upstream fix adds the !ri_cnt / !ri_buf check here — count only */

		item->ri_ops = xlog_find_item_ops(item);
		if (!item->ri_ops) {
			...
		}

		if (item->ri_ops->reorder)
			fate = item->ri_ops->reorder(item);   /* <-- unvalidated length */
```

That guard checks `item->ri_cnt` and `item->ri_buf`, i.e. that a region
*exists*. It says nothing about `item->ri_buf[0].iov_len`.
`item->ri_ops->reorder(item)` is invoked a few lines later, still inside the
gate's own loop body, with region 0 completely unvalidated for length. The fix
normalises "at least one region" and the very next statement dereferences that
region assuming it is at least 10 bytes long.

The primitive is a 2-byte (`reorder`) to 10-byte (`ra_pass2`) slab
out-of-bounds read. The values steer which sort list the item lands on and
which block is read ahead — no direct disclosure to userspace. Loud under
KASAN. Exploitability is low: denial of service on a KASAN/hardened kernel; on
a production kernel it is a silent overread that misdirects readahead.

## Trigger

`mount(2)` of a crafted XFS image. `reorder` runs in recovery PASS1 on the
first traversal of the log — the earliest of the buffer-item callbacks.

1. Craft an XFS image with a dirty log.
2. Emit a log item with a **4-byte** region 0 containing only:
   - `blf_type = XFS_LI_BUF` (offset 0-1) — needed so `xlog_find_item_ops()`
     resolves to `xlog_buf_item_ops`
   - `blf_size = 1` (offset 2-3) — needed so `xlog_recover_add_to_trans()`
     accepts `ri_total = 1`
3. `XLOG_COMMIT_TRANS`, then `mount(2)`.
4. `xlog_recover_reorder_trans()` resolves `ri_ops` via `ITEM_TYPE()`
   (in-bounds, offset 0-1), then calls `item->ri_ops->reorder(item)` →
   `xlog_recover_buf_reorder()` reads `buf_f->blf_flags` at offset 4-5, two
   bytes past the allocation, before `commit_pass1` ever runs.

The out-of-bounds read is unconditional once the crafted record is parsed; no
race is involved.

Privilege required: the ability to mount an untrusted XFS image.
`xfs_fs_type.fs_flags` is `FS_REQUIRES_DEV | FS_ALLOW_IDMAP | FS_MGTIME |
FS_LBS` — **not** `FS_USERNS_MOUNT`, so the bare `mount(2)` path needs real
`CAP_SYS_ADMIN` in `init_user_ns`. XFS is, however, a native removable-volume
filesystem: a USB stick formatted `xfs` is blkid-typed and mounted by a stock
privileged auto-mounter, so a physically-present attacker who inserts crafted
media reaches `xlog_recover()` holding no caps.

Required config: `CONFIG_XFS_FS=y`.
