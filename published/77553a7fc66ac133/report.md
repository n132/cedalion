# nvmet-auth: slab out-of-bounds write in nvmet_auth_challenge()

|  |  |
|---|---|
| Bug class | slab out-of-bounds write |
| Subsystem | drivers/nvme/target |
| Location | `drivers/nvme/target/fabrics-cmd-auth.c`:415 (`nvmet_auth_challenge()`) |

## Root cause

A size guard is taken against a struct far smaller than the one actually
written, expressed here as a `sizeof` typo.

```c
/* drivers/nvme/target/fabrics-cmd-auth.c:415 */
static int nvmet_auth_challenge(struct nvmet_req *req, void *d, int al)
{
	struct nvmf_auth_dhchap_challenge_data *data = d;
	struct nvmet_ctrl *ctrl = req->sq->ctrl;
	int ret = 0;
	int hash_len = nvme_auth_hmac_hash_len(ctrl->shash_id);
	int data_size = sizeof(*d) + hash_len;		/* <-- d is void *, sizeof(void) == 1 */

	if (ctrl->dh_tfm)
		data_size += ctrl->dh_keysize;
	if (al < data_size) {
		pr_debug("%s: buffer too small (al %d need %d)\n", __func__, al, data_size);
		return -EINVAL;
	}
	memset(data, 0, data_size);
	req->sq->dhchap_s1 = nvme_auth_get_seqnum();
	data->auth_type = NVME_AUTH_DHCHAP_MESSAGES;
	data->auth_id = NVME_AUTH_DHCHAP_MESSAGE_CHALLENGE;
	data->t_id = cpu_to_le16(req->sq->dhchap_tid);
	data->hashid = ctrl->shash_id;
	data->hl = hash_len;
	data->seqnum = cpu_to_le32(req->sq->dhchap_s1);
	req->sq->dhchap_c1 = kmalloc(data->hl, GFP_KERNEL);
	if (!req->sq->dhchap_c1)
		return -ENOMEM;
	get_random_bytes(req->sq->dhchap_c1, data->hl);
	memcpy(data->cval, req->sq->dhchap_c1, data->hl);	/* writes at offset 16 */
	if (ctrl->dh_tfm) {
		data->dhgid = ctrl->dh_gid;
		data->dhvlen = cpu_to_le16(ctrl->dh_keysize);
		ret = nvmet_auth_ctrl_exponential(req, data->cval + data->hl,
						  ctrl->dh_keysize);	/* offset 16+hl */
	}
```

`d` is declared `void *`, so `sizeof(*d)` is the GCC `sizeof(void) == 1` extension. The value
the author meant is `sizeof(*data)` — `struct nvmf_auth_dhchap_challenge_data` is
`auth_type(0) auth_id(1) rsvd1(2..3) t_id(4..5) hl(6) rsvd2(7) hashid(8) dhgid(9) dhvlen(10..11)
seqnum(12..15) cval[](16..)`, i.e. **16 bytes**. The guard therefore under-counts the fixed
header by **15 bytes**.

```c
/* include/linux/nvme.h:1888 — the 16-byte header the guard should have counted */
struct nvmf_auth_dhchap_challenge_data {
	__u8		auth_type;
	__u8		auth_id;
	__u16		rsvd1;
	__le16		t_id;
	__u8		hl;
	__u8		rsvd2;
	__u8		hashid;
	__u8		dhgid;
	__le16		dhvlen;
	__le32		seqnum;
	/* 'hl' bytes of challenge value */
	__u8		cval[];
	/* followed by 'dhvlen' bytes of DH value */
};
```

What the function actually writes into the `al`-byte buffer is:

- the 16-byte header (`auth_type` … `seqnum`), then
- `memcpy(data->cval, req->sq->dhchap_c1, data->hl)` — `hash_len` bytes at offset **16**, then
- when DH is in use, `nvmet_auth_ctrl_exponential(req, data->cval + data->hl, ctrl->dh_keysize)`
  — `dh_keysize` bytes at offset `16 + hash_len`.

so the true requirement is `al >= 16 + hash_len + dh_keysize`, while the guard only demands
`al >= 1 + hash_len + dh_keysize`. The caller allocates exactly what the attacker asked for:

```c
	al = nvmet_auth_receive_data_len(req);	/* le32_to_cpu(req->cmd->auth_receive.al) */
	if (!al) { ... goto done; }
	if (!nvmet_check_transfer_len(req, al))	/* equality, not a minimum */
		return;
	d = kmalloc(al, GFP_KERNEL);
	...
	case NVME_AUTH_DHCHAP_MESSAGE_CHALLENGE:
		if (nvmet_auth_challenge(req, d, al) < 0) {
```

An initiator choosing `al = 1 + hash_len (+ dh_keysize)` passes the guard and then has 15 bytes
written past the end of the `kmalloc(al)` allocation.

`nvmet_auth_receive_data_len()` was hardened for the other steps and *explicitly* exempts this
one, deferring to the in-function check that is the buggy one:

```c
	/*
	 * Reject too-short al before kmalloc(al), since the SUCCESS1 and
	 * FAILURE1/default builders write fixed response headers into it.
	 */
	switch (req->sq->dhchap_step) {
	case NVME_AUTH_DHCHAP_MESSAGE_CHALLENGE:
		return al;			/* <-- no minimum applied */
	case NVME_AUTH_DHCHAP_MESSAGE_SUCCESS1:
		min_len = sizeof(struct nvmf_auth_dhchap_success1_data);
		...
```

Note the contrast even within this file: `nvmet_auth_receive_data_len()` correctly writes
`sizeof(struct nvmf_auth_dhchap_success1_data)` and
`sizeof(struct nvmf_auth_dhchap_failure_data)` for the other branches. Only the CHALLENGE
builder uses `sizeof(*d)`.

**Honest bound on the impact**: for every reachable combination of `hash_len` ∈ {32, 48, 64} and
`dh_keysize` ∈ {0, 256, 384, 512, 768, 1024}, `al + 15` still fits inside the kmalloc bucket
that `kmalloc(al)` returned (e.g. `al = 33` → 64-byte object, writes to 48; `al = 289` →
512-byte object, writes to 304). So this corrupts slab padding/redzone rather than a
neighbouring object. It is a hard KASAN `slab-out-of-bounds write` and a genuine correctness
defect, but not by itself a neighbour-corruption primitive. Only `al` bytes are copied back to
the initiator (`nvmet_copy_to_sgl(req, 0, d, al)`), so nothing leaks outward either.

## Trigger

Reachability is network-remote and pre-authentication: an AUTH_RECEIVE fabrics capsule on an
unauthenticated queue. It requires `CONFIG_NVME_TARGET_AUTH=y` and an exported subsystem the
attacker can `nvmf_connect` to. No privilege is required — no local account and no valid
NVMe-oF credentials. `nvmet_parse_fabrics_admin_cmd()` (`drivers/nvme/target/fabrics-cmd.c`:104)
routes `auth_send`/`auth_receive` straight to the handlers with no `capable()`/`ns_capable()`
on the path; `nvmet_check_auth_status()` gates only *non*-fabrics commands.

1. The victim runs an NVMe-oF target with `CONFIG_NVME_TARGET_AUTH=y` and in-band DH-HMAC-CHAP
   configured, over nvmet-tcp, nvmet-rdma or nvmet-fc.
2. The attacker completes `nvmf_connect` (no credentials needed when
   `attr_allow_any_host = 1`; in any case this is before DH-HMAC-CHAP succeeds) and sends a
   valid AUTH_SEND NEGOTIATE so that `req->sq->dhchap_step` advances to
   `NVME_AUTH_DHCHAP_MESSAGE_CHALLENGE`.
3. The attacker issues AUTH_RECEIVE with `secp = NVME_AUTH_DHCHAP_PROTOCOL_IDENTIFIER`,
   `spsp0 = spsp1 = 0x01` and `al = 1 + hash_len` — for the default SHA-256 with no DH group,
   `al = 33`.
4. `nvmet_auth_receive_data_len()` returns 33 unchanged; `d = kmalloc(33)`.
5. `nvmet_auth_challenge()` computes `data_size = 1 + 32 = 33`, so `33 < 33` is false and the
   guard passes.
6. `memcpy(data->cval, req->sq->dhchap_c1, 32)` writes offsets 16..47 of a 33-byte allocation —
   15 bytes past the end. KASAN reports `slab-out-of-bounds write`.
7. With a DH group configured, `al = 1 + hash_len + dh_keysize` reaches the same 15-byte
   overrun through `nvmet_auth_ctrl_exponential()`.

The crash happens in the `nvmet_tcp_wq` worker, i.e. purely from parsing the attacker's
capsule — no local process is involved on the victim side beyond having the target exported.
