# net/dsa: slab out-of-bounds read in `brcm_leg_fcs_tag_xmit()`

|  |  |
|---|---|
| Bug class | Slab out-of-bounds read (leaked bytes emitted onto the wire) |
| Subsystem | `net/dsa` (Broadcom legacy-FCS tagger) |
| Location | `net/dsa/tag_brcm.c`:334-335 (`brcm_leg_fcs_tag_xmit()`) |
| Reference tree | `3cd8b194bf3428dfa53120fee47e827a7c495815` (line numbers below are from this commit) |

## Root cause

`brcm_leg_fcs_tag_xmit()` computes the frame's FCS with a bulk access over
`skb->data` for a length taken from `skb->len`, with no `pskb_may_pull()` /
`skb_linearize()` / `skb_headlen()` bound. `skb->len` is used against a
**linear** pointer and the walk runs `skb->data_len` bytes **off the end of the
linear allocation**.

```c
	fcs_len = skb->len;
	fcs_val = cpu_to_le32(crc32_le(~0, skb->data, fcs_len) ^ ~0);
```

**Why a nonlinear skb reaches it.** DSA strips scatter-gather from a user port
only when the tagger declares tailroom (`net/dsa/user.c:2717-2720`):

```c
	user->needed_tailroom = cpu_dp->tag_ops->needed_tailroom;
	user->needed_tailroom += conduit->needed_tailroom;
	...
	user->features = conduit->vlan_features | NETIF_F_HW_TC;
	if (user->needed_tailroom)
		user->features &= ~(NETIF_F_SG | NETIF_F_FRAGLIST);
```

`brcm_legacy_fcs_netdev_ops` (`net/dsa/tag_brcm.c:361-367`) declares
`.needed_headroom = BRCM_LEG_TAG_LEN` and **no `.needed_tailroom`** — even
though the very same xmit function appends `ETH_FCS_LEN` bytes at line 356.
With a conduit that itself needs no tailroom (the normal case for an Ethernet
conduit), `user->needed_tailroom == 0`, so `NETIF_F_SG` is inherited from
`conduit->vlan_features` and **never stripped**. `validate_xmit_skb()`
therefore does not linearize, and paged skbs arrive at the tagger.

Nothing on the path flattens them before the `crc32_le()`:

- `skb_ensure_writable_head_tail()` (`net/dsa/user.c:925`) is
  `pskb_expand_head()`-based — it un-shares and grows head/tail but
  **preserves the frags**.
- `eth_skb_pad(skb)` (`user.c:934-935`) is gated on `dev->needed_tailroom`,
  which is 0 here, so it is skipped.
- `__skb_put_padto(skb, ETH_ZLEN + BRCM_LEG_TAG_LEN, false)` at line 331 is a
  no-op for any frame already >= 70 bytes.
- `__skb_pad(skb, ETH_FCS_LEN, false)` at line 356 *does* call
  `skb_linearize()` internally — but that is **after** the `crc32_le()` has
  already run.

So `crc32_le()` walks `skb->data_len` bytes beyond `skb_headlen(skb)` into
adjacent slab memory.

The relevant code in full:

```c
/* net/dsa/tag_brcm.c:331-356 */
	if (__skb_put_padto(skb, ETH_ZLEN + BRCM_LEG_TAG_LEN, false))
		return NULL;                       /* no-op for frames >= 70 bytes */

	fcs_len = skb->len;                        /* WHOLE-frame length ... */
	fcs_val = cpu_to_le32(crc32_le(~0, skb->data, fcs_len) ^ ~0);  /* ... over the LINEAR head */

	skb_push(skb, BRCM_LEG_TAG_LEN);
	dsa_alloc_etype_header(skb, BRCM_LEG_TAG_LEN);
	brcm_tag = skb->data + 2 * ETH_ALEN;
	...
	brcm_tag[2] = BRCM_LEG_EGRESS | BRCM_LEG_LEN_HI(fcs_len);
	brcm_tag[3] = BRCM_LEG_LEN_LO(fcs_len);
	...
	if (__skb_pad(skb, ETH_FCS_LEN, false))    /* linearizes -- but too late */
		return NULL;
	skb_put_data(skb, &fcs_val, ETH_FCS_LEN);

/* net/dsa/tag_brcm.c:361-367 — no .needed_tailroom despite appending ETH_FCS_LEN */

	.name = BRCM_LEGACY_FCS_NAME,
	.proto = DSA_TAG_PROTO_BRCM_LEGACY_FCS,
	.xmit = brcm_leg_fcs_tag_xmit,
	.rcv = brcm_leg_tag_rcv,
	.needed_headroom = BRCM_LEG_TAG_LEN,

```

**Two observable consequences.** The CRC is computed over out-of-bounds heap
bytes and then transmitted, and `fcs_len` (`= skb->len`, the full frame length)
is written into the Broadcom tag's length field at lines 348-349 while the FCS
covers the wrong bytes — so the switch receives a frame whose declared length,
real payload and FCS all disagree.

The primitive is an out-of-bounds **read** of up to ~`skb->data_len` bytes (~1.5 KB) past
the linear slab object. The bytes are not returned to userspace directly, but
they are folded into a CRC32 that is transmitted; the data is laundered through
CRC32 before leaving the box, so recovering plaintext requires brute-forcing 4
bytes at a time. There is no write primitive.

The sibling `brcm_leg_tag_xmit()` (non-FCS variant) does not compute a CRC and
so is unaffected, which is probably why the omission survived.

## Trigger

1. Target is a board using a Broadcom legacy-FCS DSA switch —
   `CONFIG_NET_DSA_TAG_BRCM_LEGACY_FCS`, i.e. the b53 `is5325()`/`is5365()`
   families (`drivers/net/dsa/b53/b53_common.c`) — whose conduit advertises
   `NETIF_F_SG` in `vlan_features` (the common case). `CONFIG_NET_DSA` must be
   enabled for the buggy file to be compiled at all.
2. A local process opens `AF_PACKET`/`SOCK_RAW` on a DSA user port (e.g.
   `lan1`) with `PACKET_VNET_HDR` enabled.
3. It transmits a frame large enough that `packet_snd()` splits it:
   `net/packet/af_packet.c` sets
   `linear = max(vnet_hdr.hdr_len, min(len, dev->hard_header_len))`, so with a
   small declared `hdr_len` only ~14 bytes stay linear and the remainder goes
   into page frags.
4. `dsa_user_xmit()` → `brcm_leg_fcs_tag_xmit()` runs
   `crc32_le(~0, skb->data, skb->len)` over a ~14-byte linear head with
   `skb->len` ~ 1500, reading ~1486 bytes of adjacent slab memory.
5. Under KASAN this is a `slab-out-of-bounds` read. Without KASAN the
   out-of-bounds bytes are folded into the transmitted CRC and the frame goes
   out with a corrupt FCS.

The condition the attacker controls is the linear/paged split of the egress
skb: the larger the paged portion, the further past the end of the `skb->head`
slab object the CRC walk runs. It is deterministic; there is no race.

**Privilege required.** `CAP_NET_RAW` in the owning user namespace for the raw
socket path. The bug is also reachable without raw sockets by any ordinary
socket whose egress skb happens to be paged (TCP/UDP sendfile, `MSG_ZEROCOPY`,
forwarded GRO traffic), since the port advertises SG — that path needs no
capability at all.

On x86, note that `crc32_le()` dispatches to the PCLMULQDQ implementation
(`crc32_lsb_pclmul()`) for any length >= 16
(`lib/crc/x86/crc-pclmul-template.h:56`). That is hand-written assembly, which
the compiler does not instrument, so KASAN cannot see the out-of-bounds loads
there. The read happens either way; only its visibility to the sanitizer
differs.
