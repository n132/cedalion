# libceph: slab out-of-bounds write in `read_partial_message_chunk()` — peer-declared `middle_len` never checked against an already-allocated `msg->middle`

|  |  |
|---|---|
| Bug class | slab out-of-bounds write (remote heap buffer overflow) |
| Subsystem | `net/ceph` (libceph) |
| Location | `net/ceph/messenger.c:2101` (`ceph_con_in_msg_alloc()`), `net/ceph/messenger_v2.c:2929` (`__handle_control()`), `net/ceph/messenger_v1.c:967` (`read_partial_message_chunk()`) |

## Root cause

A peer-declared length is trusted against a buffer whose size was fixed by an
*earlier, different* message, and the capacity check that exists for the front
segment has no counterpart for the middle segment.

`ceph_con_in_msg_alloc()` allocates the middle buffer only when the message does
not already have one:

```c
/* net/ceph/messenger.c:2101 — allocation skipped when a (smaller) buffer already exists */
	memcpy(&con->in_msg->hdr, hdr, sizeof(*hdr));

	if (middle_len && !con->in_msg->middle) {
		ret = ceph_alloc_middle(con, con->in_msg);
		if (ret < 0) {
			ceph_msg_put(con->in_msg);
			con->in_msg = NULL;
		}
	}
```

and `ceph_alloc_middle()` sizes the buffer from the current message's header:

```c
/* net/ceph/messenger.c:2038 */
static int ceph_alloc_middle(struct ceph_connection *con, struct ceph_msg *msg)
{
	int middle_len = le32_to_cpu(msg->hdr.middle_len);
	...
	BUG_ON(!middle_len);
	BUG_ON(msg->middle);

	msg->middle = ceph_buffer_new(middle_len, GFP_NOFS);
```

The `!con->in_msg->middle` guard means that if the message *already* carries a
middle buffer, its size is whatever a previous message chose — and **nothing ever
compares the new peer-declared `middle_len` against that existing
`msg->middle->alloc_len`**.

That matters because several incoming messages are **preallocated and permanently
owned by the monitor client**: `monc->m_subscribe_ack` (`mon_client.c:1190`) and
`monc->m_auth_reply` (`mon_client.c:1201`). `mon_alloc_msg()` hands the same
`struct ceph_msg` back for every `CEPH_MSG_MON_SUBSCRIBE_ACK` /
`CEPH_MSG_AUTH_REPLY` via `ceph_msg_get()`. `msg->middle` is released in exactly
one place — `ceph_msg_release()` (`messenger.c:2170`) — which runs only on the
final reference drop. `monc` holds a permanent reference for the whole mount
lifetime, so `ceph_msg_release()` never runs and the middle buffer, once attached,
**persists across messages forever**.

The receive path then trusts the new `middle_len` with only an advisory `WARN_ON`:

```c
/* net/ceph/messenger_v2.c:2929, __handle_control() */
	if (middle_len(msg)) {
		WARN_ON(middle_len(msg) > msg->middle->alloc_len);	/* advisory only */
		msg->middle->vec.iov_len = middle_len(msg);
	} else if (msg->middle) {
		msg->middle->vec.iov_len = 0;
	}

/* net/ceph/messenger_v2.c:2032, prepare_read_tail_plain() */
	if (middle_len(msg)) {
		add_in_kvec(con, msg->middle->vec.iov_base, middle_len(msg));
		WARN_ON(msg->middle->vec.iov_len != middle_len(msg));
	}
```

`add_in_kvec()` arms a socket read of `middle_len(msg)` bytes straight into the
old, smaller `ceph_buffer`. msgr1 is identical via
`read_partial_message_section()` → `read_partial_message_chunk()`
(`messenger_v1.c:967`), whose `while (section->iov_len < sec_len)` loop recvs into
`iov_base + iov_len` with no capacity bound whatsoever:

```c
/* net/ceph/messenger_v1.c:967 — msgr1 has no bound at all */
	while (section->iov_len < sec_len) {
		BUG_ON(section->iov_base == NULL);
		left = sec_len - section->iov_len;
		ret = ceph_tcp_recvmsg(con->sock, (char *)section->iov_base +
				       section->iov_len, left);
```

`middle_len` is bounded only by `CEPH_MSG_MAX_MIDDLE_LEN` (`decode_preamble()` at
`messenger_v2.c:536`, `read_partial_message()` at `messenger_v1.c:1174`), so the
attacker picks both the size and the content of the overflow.

The front segment has exactly this check — `mon_alloc_msg()` at
`mon_client.c:1539` reallocates when `front_len > m->front_alloc_len`, and
`get_reply()` at `osd_client.c:5445` does the same for OSD replies. There is no
middle-side equivalent anywhere in the tree. The `!con->in_msg->middle` condition
reads as a harmless "don't allocate twice" optimisation; that it also silently
accepts a *larger* length on the second message is not visible from the allocation
site. The `BUG_ON(msg->middle)` inside `ceph_alloc_middle()` shows the author
expected the buffer to be fresh each time — an expectation the preallocated monc
messages break.

## Trigger

The attacker is the monitor peer: a malicious or compromised mon, an address
takeover, or an on-path attacker (default msgr2 mode is `crc` with no encryption;
msgr1 has none at all). `net/ceph/auth.c:19` advertises `CEPH_AUTH_NONE`, so no
key is needed. The victim only needs a CephFS mount or RBD mapping; no victim-side
action is required at the time of the attack, since both message types used are
ones the monitor sends unprompted.

1. **Priming message.** The monitor sends a `CEPH_MSG_MON_SUBSCRIBE_ACK` (or
   `CEPH_MSG_AUTH_REPLY`) declaring a small `middle_len`, e.g. 16.
   `mon_alloc_msg()` returns `ceph_msg_get(monc->m_subscribe_ack)`;
   `ceph_con_in_msg_alloc()` sees `!msg->middle` and calls `ceph_alloc_middle()` →
   `ceph_buffer_new(16)`. That 16-byte buffer is now attached to the long-lived
   `monc->m_subscribe_ack` permanently.
2. **Overflow message.** The monitor sends a second message of the *same type*
   declaring `middle_len = 0x1000` (anything up to `CEPH_MSG_MAX_MIDDLE_LEN`, i.e.
   16 MiB).
3. `ceph_con_in_msg_alloc()` skips the allocation because `con->in_msg->middle` is
   already set. `__handle_control()` WARNs and sets
   `msg->middle->vec.iov_len = 0x1000`.
4. `prepare_read_tail_plain()` arms
   `add_in_kvec(con, msg->middle->vec.iov_base, 0x1000)` — a 4096-byte socket read
   into the 16-byte `ceph_buffer` → 4080 bytes of attacker-chosen data written past
   a `kmalloc-16` object.

The attacker controls the size of the victim buffer (via the priming message, so
the target slab cache is selectable from `kmalloc-8` upward), the length of the
overflow (up to 16 MiB) and every overflowing byte, and can repeat the
priming/overflow pair at will. The `WARN_ON` fires first, so on a `panic_on_warn`
kernel this degrades to a DoS; otherwise the WARN is a splat and the corruption
proceeds.

**Privilege / configuration.** The attacker needs no local account, capability or
namespace on the victim — the input is remote. The victim's mount needs
`CAP_SYS_ADMIN` in the initial user namespace. Requires `CONFIG_CEPH_LIB` with a
Ceph client in use (`CONFIG_CEPH_FS` or `CONFIG_BLK_DEV_RBD`).
