# drbd: unvalidated digest length in `receive_DataRequest()` — oversized `kmalloc()` WARN and short-digest slab OOB read

|  |  |
|---|---|
| Bug class | Peer-triggered WARN → panic under `panic_on_warn` + slab out-of-bounds read |
| Subsystem | `drivers/block/drbd` |
| Location | `drivers/block/drbd/drbd_receiver.c:2713-2726` (`receive_DataRequest()`); consumers `w_e_end_csum_rs_req()`, `w_e_end_ov_reply()` in `drivers/block/drbd/drbd_worker.c` |

## Root cause

`P_CSUM_RS_REQUEST` and `P_OV_REPLY` take a digest length straight off the wire, use it to size an
allocation and a socket read, and validate it at neither point.

`decode_header()` (`drbd_receiver.c`) takes a full 32-bit length off the wire for both the
`p_header100` and `p_header95` framings (the latter is selected by the 2-byte `DRBD_MAGIC_BIG`
magic, so a 32-bit length is reachable regardless of the negotiated protocol version):

```c
		pi->size = be32_to_cpu(h->length);
```

In the `drbdd()` dispatch loop the only checks applied are:

```c
		if (pi.size > shs && !cmd->expect_payload) { ... goto err_out; }
		if (pi.size < shs) { ... goto err_out; }
		if (shs) {
			err = drbd_recv_all_warn(connection, pi.data, shs);
			...
			pi.size -= shs;
		}
```

`P_CSUM_RS_REQUEST` and `P_OV_REPLY` both have `expect_payload = 1`, so the "No payload expected"
upper check is skipped entirely, and `pi.size >= shs` merely guarantees the fixed
`struct p_block_req` was present. The residual `pi->size` after the subtraction is **entirely
unconstrained** — anywhere in `[0, 2^32-1-shs]`.

`receive_DataRequest()` validates `sector` and `blksize` carefully (`:2643-2651`: `size <=
DRBD_MAX_BIO_SIZE`, alignment, capacity) and then uses the unvalidated digest length:

```c
/* drivers/block/drbd/drbd_receiver.c:2713 — no floor, no ceiling */
	case P_OV_REPLY:
	case P_CSUM_RS_REQUEST:
		di = kmalloc(sizeof(*di) + pi->size, GFP_NOIO);
		if (!di)
			goto out_free_e;

		di->digest_size = pi->size;
		di->digest = (((char *)di)+sizeof(struct digest_info));

		peer_req->digest = di;
		peer_req->flags |= EE_HAS_DIGEST;

		if (drbd_recv_all(peer_device->connection, di->digest, pi->size))
			goto out_free_e;
```

**Arm 1 — missing ceiling ⇒ peer-triggered WARN.** Declare a length
of `shs + 8 MiB`. `kmalloc(8 MiB + 16, GFP_NOIO)` exceeds `KMALLOC_MAX_CACHE_SIZE`, so
`__do_kmalloc_node` (`mm/slub.c:5401`) routes it to `___kmalloc_large_node()` (`mm/slub.c:5341`),
which calls `alloc_frozen_pages_noprof(flags, get_order(8 MiB) = 11)` with no order check of its
own. The page allocator then hits `mm/page_alloc.c:5340`:

```c
	return !(WARN_ON_ONCE_GFP(order > MAX_PAGE_ORDER, gfp));
```

`MAX_PAGE_ORDER` is 10 (4 MiB) on x86_64 and `GFP_NOIO` carries no `__GFP_NOWARN`, so the WARN
fires — from the `drbd_receiver` kthread, i.e. remotely triggered. Under `panic_on_warn` that is a
remote panic. The allocation happens **before** any payload is read, so the attacker only has to
send ~32 bytes.

**Arm 2 — missing floor ⇒ slab out-of-bounds read.** `pi->size == 0` (or any value below the
digest size) is equally legal. `di->digest` then points at the end of a 16-byte allocation and
`drbd_recv_all(..., 0)` is a silent no-op. Later, in worker context:

```c
/* drivers/block/drbd/drbd_worker.c:1176 — D_ASSERT does not stop anything */
			digest_size = crypto_shash_digestsize(peer_device->connection->csums_tfm);
			D_ASSERT(device, digest_size == di->digest_size);
			digest = kmalloc(digest_size, GFP_NOIO);
		}
		if (digest) {
			drbd_csum_ee(peer_device->connection->csums_tfm, peer_req, digest);
			eq = !memcmp(digest, di->digest, digest_size);   /* OOB when di->digest_size < digest_size */
			kfree(digest);
		}
```

`D_ASSERT` is **not** an assertion — `drbd_polymorph_printk.h:121` defines it as a bare
`drbd_err()` printk with no control-flow effect:

```c
/* drivers/block/drbd/drbd_polymorph_printk.h:121 — it is a printk, not an assert */
#define D_ASSERT(x, exp)							\
	do {									\
		if (!(exp))							\
			drbd_err(x, "ASSERTION %s FAILED in %s\n",		\
				#exp, __func__);				\
	} while (0)
```

So execution proceeds into `memcmp(digest, di->digest, digest_size)`, reading `digest_size`
(4–64 bytes depending on the negotiated `csums_tfm`) past the end of a 16-byte slab object —
a slab out-of-bounds read. `w_e_end_ov_reply()` (`:1302`) has the identical pattern with
`verify_tfm`.

**Why it is not already fixed here**: every *other* `pi->size` consumer in this file is bounded —
`:3471` (`pi->size > sizeof(integrity_alg)`), `:3685` (`pi->size > exp_max_sz`), `:4665`/`:4670`
(bitmap bounds), `:5237`/`:5243` (auth: `> CHALLENGE_LEN*2` and `< CHALLENGE_LEN`, i.e. both a floor
and a ceiling), and `receive_bitmap_plain()` at `:4466` even carries an explicit
`if (want == 0) return 0;`. `:2715` is the single entry point in the receive path with neither. The
correct bound is available locally and unused: `crypto_shash_digestsize(connection->csums_tfm)` /
`verify_tfm` is already known at receive time, so the check should be an exact-size gate.

## Trigger

The bug is reached over the DRBD replication link, in the `drbd_receiver` kthread that processes
data straight off the socket. It requires `CONFIG_BLK_DEV_DRBD=y`; for arm 2 the connection must
also have negotiated a `csums-alg` / `verify-alg` so `csums_tfm` / `verify_tfm` is non-NULL.

1. Victim runs DRBD with a resource configured and listening (`drbdadm up`). DRBD peer
   authentication (`cram-hmac-alg` + `shared-secret`) is **optional** and off by default, so any
   host that can reach the DRBD port can become the peer; otherwise the attacker is a compromised
   peer node or on-path (DRBD's replication link has no transport encryption).
2. The attacker completes the handshake and reaches the `drbdd()` receive loop.
3. **Arm 1 (WARN/panic):** the attacker sends a `P_CSUM_RS_REQUEST` packet header declaring
   `length = sizeof(struct p_block_req) + 0x800000`, followed by a valid `p_block_req` body
   (in-range `sector`, `blksize`). `receive_DataRequest()` reaches
   `kmalloc(0x800010, GFP_NOIO)` → order 11 > `MAX_PAGE_ORDER` → `WARN_ON_ONCE_GFP` → panic under
   `panic_on_warn`. No payload is ever sent.
4. **Arm 2 (OOB read):** the attacker sends `P_CSUM_RS_REQUEST` (or `P_OV_REPLY`) declaring
   `length = sizeof(struct p_block_req)` exactly, so the residual digest length is `0`. The peer
   request is queued; when the worker runs `w_e_end_csum_rs_req()`, `memcmp()` reads
   `crypto_shash_digestsize(csums_tfm)` bytes from a 16-byte object.

No local privilege is required of the attacker beyond network reachability of the DRBD port (or a
compromised peer node). DRBD links are commonly on a private replication network, which narrows
but does not eliminate exposure.
