# security/keys/trusted-keys: slab out-of-bounds read in tpm2_load_cmd()

|  |  |
|---|---|
| Bug class | Slab out-of-bounds read |
| Subsystem | security/keys/trusted-keys |
| Location | `security/keys/trusted-keys/trusted_tpm2.c`:430-458 (`tpm2_load_cmd()`), buffer allocated at :119 (`tpm2_key_decode()`) |

## Root cause

`tpm2_load_cmd()` bounds every offset against `payload->blob_len` (the DER
container length) while the buffer it indexes was allocated as
`priv_len + pub_len + 4`.

`tpm2_key_decode()` ASN.1-decodes the user's DER blob and allocates a working
buffer from the **decoded octet-string lengths**:

```c
/* security/keys/trusted-keys/trusted_tpm2.c — tpm2_key_decode() */
	ret = asn1_ber_decoder(&tpm2key_decoder, &ctx, payload->blob,
			       payload->blob_len);
	if (ret < 0)
		return ret;

	if (ctx.priv_len + ctx.pub_len > MAX_BLOB_SIZE)
		return -EINVAL;

	blob = kmalloc(ctx.priv_len + ctx.pub_len + 4, GFP_KERNEL);
	if (!blob)
		return -ENOMEM;

	*buf = blob;
	options->keyhandle = ctx.parent;

	memcpy(blob, ctx.priv, ctx.priv_len);
	blob += ctx.priv_len;
	memcpy(blob, ctx.pub, ctx.pub_len);
```

The allocation is therefore `priv_len + pub_len + 4` bytes.

`tpm2_load_cmd()` then parses that buffer — but every bound it checks is
against `payload->blob_len`, which is the length of the **whole DER
container**, not of the allocation:

```c
/* security/keys/trusted-keys/trusted_tpm2.c — tpm2_load_cmd() */
	rc = tpm2_key_decode(payload, options, &blob);
	if (rc) {
		/* old form */
		blob = payload->blob;
		payload->old_format = 1;
	} else {
		blob_ref = blob;
	}
	...
	/* must be big enough for at least the two be16 size counts */
	if (payload->blob_len < 4)
		return -EINVAL;

	private_len = get_unaligned_be16(blob);

	/* must be big enough for following public_len */
	if (private_len + 2 + 2 > (payload->blob_len))
		return -E2BIG;

	public_len = get_unaligned_be16(blob + 2 + private_len);	/* OOB read */
	if (private_len + 2 + public_len + 2 > payload->blob_len)
		return -E2BIG;

	pub = blob + 2 + private_len + 2;
	/* key attributes are always at offset 4 */
	attrs = get_unaligned_be32(pub + 4);				/* OOB read */
	...
	blob_len = private_len + public_len + 4;
	if (blob_len > payload->blob_len)
		return -E2BIG;
	...
	tpm_buf_append(&buf, blob, blob_len);				/* OOB read */
```

All four guards — `payload->blob_len < 4`, `private_len + 4 > blob_len`,
`private_len + public_len + 4 > blob_len`, and `blob_len > payload->blob_len` —
use `payload->blob_len`. None uses `ctx.priv_len + ctx.pub_len + 4`.

The DER container is strictly larger than its two octet strings: it also
carries the OID, an optional BOOLEAN, the `parent` INTEGER and all the TLV
headers. Crucially the attacker can inflate it arbitrarily —
`tpm2_key_parent()` (`trusted_tpm2.c:131`) accepts an INTEGER of any length (it
simply shifts every content byte into a `u32` with no length limit), so padding
`parent` with leading zero bytes grows `payload->blob_len` without changing
`priv_len` or `pub_len`. `asn1_ber_decoder` is BER, so non-minimal INTEGER
encodings are accepted.

So: supply a DER blob with 2-byte `priv` and 2-byte `pub` (allocation = 8
bytes, `kmalloc-8`) and a long `parent` INTEGER bringing `payload->blob_len` to,
say, 200. Then `private_len = get_unaligned_be16(blob)` — read from the
attacker's own 2 `priv` bytes, so freely chosen up to `blob_len - 4` = 196 —
passes every check, and:

- `get_unaligned_be16(blob + 2 + private_len)` reads at offset up to 198 of an
  8-byte object,
- `get_unaligned_be32(pub + 4)` reads further still,
- `tpm_buf_append(&buf, blob, blob_len)` copies up to `blob_len` bytes out of
  the 8-byte object and sends them to the TPM.

**Why it is not already fixed**: in the legacy path the two lengths genuinely
coincide — when `tpm2_key_decode()` fails, `blob = payload->blob` and
`payload->blob_len` *is* the size of that buffer. The checks were written for
that case and read as correct. When the ASN.1 path succeeds, `blob` points at a
different, smaller allocation and the same expressions silently become
meaningless. Nothing downstream re-derives the real size — `blob_ref` is only
used for `kfree`.

The resulting primitive is a slab out-of-bounds **read** of attacker-chosen
length (up to `MAX_BLOB_SIZE`) from an attacker-chosen small cache
(`priv_len`/`pub_len` select the allocation size), with the over-read bytes
forwarded to the TPM in the `TPM2_CC_LOAD` command. Whether they come back to
the attacker depends on the TPM's response, so the direct disclosure channel is
weak; the reliable effects are a KASAN `slab-out-of-bounds` and a page-fault
oops when the allocation sits at the end of a slab page. There is no write
primitive.

Both out-of-bounds reads happen **before** `tpm2_start_auth_session()` or any
`tpm_transmit_cmd()`, so the TPM only has to exist, not to behave.

## Trigger

1. System with a TPM 2.0 chip, `CONFIG_TCG_TPM` and `CONFIG_TRUSTED_KEYS` with
   the TPM2 backend active (the default when a TPM 2.0 is present).
   `CONFIG_TRUSTED_KEYS_TPM` is `default y` in Kconfig once `TRUSTED_KEYS` is
   on, so this is the stock configuration for any kernel that ships trusted
   keys; `CONFIG_ASN1` and `CONFIG_OID_REGISTRY` are pulled in with it. Without
   `CONFIG_TRUSTED_KEYS` / `CONFIG_TRUSTED_KEYS_TPM` the vulnerable file is not
   compiled at all. `trusted_tpm_init()`
   (`security/keys/trusted-keys/trusted_tpm1.c:959`) runs at `late_initcall` and
   returns `-ENODEV` unless `tpm_default_chip()` succeeds, and
   `trusted_tpm_unseal()` only dispatches to `tpm2_unseal_trusted()` when
   `tpm_is_tpm2(chip)` is true.
2. As an ordinary unprivileged user, craft a DER `TPMKey` structure per
   `security/keys/trusted-keys/tpm2key.asn1` containing:
   - the TPM key OID,
   - a `parent` INTEGER padded with many leading zero bytes (e.g. 150 bytes) so
     the container is large, and non-zero so the `if (!options->keyhandle)`
     guard is satisfied,
   - a 2-byte `privkey` OCTET STRING whose value is the desired `private_len`
     big-endian,
   - a 2-byte `pubkey` OCTET STRING.
3. `add_key("trusted", "k", "load <hex-DER> keyhandle=0x81000001", len,
   KEY_SPEC_PROCESS_KEYRING)` — `add_key(2)` with type `"trusted"` requires no
   capability.
4. `datablob_parse()` (`trusted_core.c:110`) sets `payload->blob_len` to the
   full DER length — `strlen(hex)/2`, capped at `MAX_BLOB_SIZE` = 1152
   (`include/keys/trusted-type.h:23`, the `CONFIG_TCG_TPM` value);
   `tpm2_key_decode()` allocates only 8 bytes.
5. `tpm2_load_cmd()` validates the attacker's `private_len` against the 200-byte
   container length and then reads and copies far past the 8-byte allocation.

**Privilege required**: none. `add_key(2)` with key type `"trusted"` and a
`load <hex>` payload is reachable by a fully unprivileged local user (uid != 0,
no capabilities, no namespaces). No `capable()` / `ns_capable()` / LSM-cap check
exists anywhere on the path `__do_sys_add_key` → `key_create_or_update` →
`__key_instantiate_and_link` → `trusted_instantiate` (`trusted_core.c:154`) →
`trusted_tpm_unseal` (`trusted_tpm1.c:897`) → `tpm2_unseal_trusted`
(`trusted_tpm2.c:584`) → `tpm2_load_cmd` (`trusted_tpm2.c:370`);
`trusted_instantiate` only bounds `datalen` (0 < datalen <= 32767).

Both the out-of-bounds offset and the size of the source allocation are under
attacker control, and the trigger is deterministic.
