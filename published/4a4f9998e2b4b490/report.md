# drivers/scsi/sd_zbc: slab out-of-bounds read in sd_zbc_report_zones()

|  |  |
|---|---|
| Bug class | slab out-of-bounds read (potential info leak) |
| Subsystem | drivers/scsi |
| Location | `drivers/scsi/sd_zbc.c:~250` (`sd_zbc_report_zones()`) |

## Root cause

The buffer is allocated by `sd_zbc_alloc_report_buffer()`, which computes an *ideal* size and then shrinks
it repeatedly against real hardware constraints:

```c
	nr_zones = min(nr_zones, sdkp->zone_info.nr_zones);
	bufsize = roundup((nr_zones + 1) * 64, SECTOR_SIZE);
	bufsize = min_t(size_t, bufsize,
			queue_max_hw_sectors(q) << SECTOR_SHIFT);
	max_segments = min(BIO_MAX_INLINE_VECS, queue_max_segments(q));
	bufsize = min_t(size_t, bufsize, max_segments << PAGE_SHIFT);

	while (bufsize >= SECTOR_SIZE) {
		buf = kvzalloc(bufsize, GFP_KERNEL | __GFP_NORETRY);
		if (buf) {
			*buflen = bufsize;
			return buf;
		}
		bufsize = rounddown(bufsize >> 1, SECTOR_SIZE);	/* halves on ENOMEM */
	}
```

So `buflen` is routinely **far below** `64 * nr_zones` — that is the normal case, not an edge case, which
is exactly why the caller re-issues the command in a loop.

But the caller's own `nr_zones` is never reduced, and the per-iteration descriptor count is taken
**straight off the wire** with no reference to `buflen`:

```c
	while (zone_idx < nr_zones && lba < sdkp->capacity) {
		ret = sd_zbc_do_report_zones(sdkp, buf, buflen, lba, true);
		if (ret)
			goto out;

		offset = 0;
		nr = min(nr_zones, get_unaligned_be32(&buf[0]) / 64);
		if (!nr)
			break;

		for (i = 0; i < nr && zone_idx < nr_zones; i++) {
			offset += 64;
			start_lba = get_unaligned_be64(&buf[offset + 16]);
			zone_length = get_unaligned_be64(&buf[offset + 8]);
```

`buf[0..3]` is the ZONE LIST LENGTH, written by the drive. The only validation applied to it is a **floor**,
inside `sd_zbc_do_report_zones()`:

```c
	rep_len = get_unaligned_be32(&buf[0]);
	if (rep_len < 64) {
		sd_printk(KERN_ERR, sdkp,
			  "REPORT ZONES report invalid length %u\n", rep_len);
		return -EIO;
	}
```

There is **no ceiling against `buflen`**. A drive reporting a large ZONE LIST LENGTH makes
`nr = rep_len / 64` up to ~67 million, and `offset` (a `size_t`) then steps in 64-byte increments with no
relation whatsoever to the allocation. The reads at `buf[offset + 16]` and `buf[offset + 8]` walk straight
off the end of the `kvzalloc()`'d object.

The sanity checks inside the loop do not save it: `start_lba != lba` is evaluated **after** the
out-of-bounds reads that produce `start_lba`, so the first iteration past the end of the buffer has already
read OOB. In practice the walk aborts within a descriptor or two with `-EINVAL`, but when `bufsize` lands
page-aligned `kvzalloc()` may fall back to vmalloc and the overread hits a guard page instead. If the
adjacent heap bytes happen to satisfy the LBA continuity check, `sd_zbc_parse_report()` copies 64
out-of-bounds bytes into the `BLKREPORTZONE` reply returned to userspace.

**Why it is NOT already fixed there**: the `min()` has only two terms, and neither is buffer-derived. The
NVMe driver implements the identical algorithm **correctly**, with the missing third term:

```c
/* drivers/nvme/host/zns.c:214 */
		nz = min3((unsigned int)le64_to_cpu(report->nr_zones),
			  nr_zones - zone_idx, max_in_buf);
```
where `max_in_buf = (buflen - sizeof(struct nvme_zone_report)) / sizeof(struct nvme_zone_descriptor)`.
`sd_zbc` has no `max_in_buf` equivalent anywhere in the file.

## Trigger

1. Attach a device that identifies as `TYPE_ZBC` — a malicious or firmware-modified USB-storage / UAS
   drive, a crafted virtual SCSI target (tgt/LIO/QEMU), or a reprogrammed device.
2. The probe path alone is sufficient — no userspace action is required. `blk_revalidate_disk_zones()`
   (`block/blk-zoned.c`) calls `report_zones(disk, 0, UINT_MAX, ...)` during disk enumeration, so
   `nr_zones == UINT_MAX` and the `min()` degenerates entirely to the device-supplied value.
3. The device answers REPORT ZONES with a small amount of actual data but sets ZONE LIST LENGTH in
   `buf[0..3]` to a large value (e.g. 0x0FFFFFFF), making `nr` vastly exceed the number of descriptors that
   fit in `buflen`.
4. `sd_zbc_report_zones()` walks past the end of the buffer. On a KASAN kernel this is a
   `slab-out-of-bounds in sd_zbc_report_zones` splat.
5. Alternatively, reachable post-probe from userspace via `BLKREPORTZONE` / `BLKREPORTZONEV2`
   (`block/ioctl.c`), which carries no `capable()` gate, by any process that can open the zoned block
   device.

Reachability is automatic on device probe for any device claiming `TYPE_ZBC` — including a hot-plugged USB
mass-storage / UAS device, which makes this reachable at the physical-access boundary with no login — and
also reachable post-probe through the ungated `BLKREPORTZONE` ioctl. The primitive is a slab out-of-bounds
**read**: in the common case a bounded overread that aborts on the LBA continuity check; in the favourable
case for an attacker, 64 bytes of adjacent heap memory per descriptor copied into the `BLKREPORTZONE` reply
(an info leak); the vmalloc fallback path turns it into a guard-page oops (DoS). No write primitive. The
code is built when `CONFIG_BLK_DEV_ZONED` is set together with SCSI disk support (`CONFIG_SCSI` /
`CONFIG_BLK_DEV_SD`); the USB-device reach additionally needs `CONFIG_USB_STORAGE`.

Privilege required: none in the malicious-device scenario (physical access / control of a virtual SCSI
target / a passed-through USB device). For the ioctl path, the ability to open the zoned block device.
