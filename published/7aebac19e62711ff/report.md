# nfsd: slab out-of-bounds read in `clientstr_hashval()`

|  |  |
|---|---|
| Bug class | Heap out-of-bounds read |
| Subsystem | `fs/nfsd` |
| Location | `fs/nfsd/nfs4state.c`:1437-1440 (`clientstr_hashval()`), :562-570 (`opaque_hashval()`) |
| Audited commit | `3cd8b194bf3428dfa53120fee47e827a7c495815` |

## Root cause

`nfsd4_decode_opaque()` correctly rejects the zero-length case:

```c
/* fs/nfsd/nfs4xdr.c:197-215 */
static __be32
nfsd4_decode_opaque(struct nfsd4_compoundargs *argp, struct xdr_netobj *o)
{
	...
	if (len == 0 || len > NFS4_OPAQUE_LIMIT)
		return nfserr_bad_xdr;
	...
	o->len = len;
	return nfs_ok;
}
```

So a `client_owner4.co_ownerid` of **1 to 7 bytes** is entirely legal.
`alloc_client()` stores it via `xdr_netobj_dup()` → `kmemdup(data, len)` — a
*tight* allocation, unlike the decode scratch buffer it came from.

The hash function then ignores `name.len` and reads a hardcoded 8 bytes:

```c
/* fs/nfsd/nfs4state.c:1437-1440 */
static unsigned int clientstr_hashval(struct xdr_netobj name)
{
	return opaque_hashval(name.data, 8) & CLIENT_HASH_MASK;
	                                 /* ^ ignores name.len */
}

/* fs/nfsd/nfs4state.c:562-570 */
static inline u32
opaque_hashval(const void *ptr, int nbytes)
{
	unsigned char *cptr = (unsigned char *) ptr;

	u32 x = 0;
	while (nbytes--) {
		x *= 37;
		x += *cptr++;
	}
	...
}
```

`opaque_hashval(ptr, 8)` unconditionally walks 8 bytes. For a 1–7 byte
`co_ownerid` this reads past the end of the `kmemdup`'d object. The allocation
lands in the `kmalloc-8` bucket, so nothing faults — but KASAN tracks the
*requested* size, so this is a reportable slab-out-of-bounds read.

Nothing enforces `len >= 8` anywhere on the path — not the decoder, not
`alloc_client()`, not the callers at lines 8865/8915. The constant `8` appears
to be a fossil from when the table was keyed by fixed-length `recdir` names.
The `compare_blob()` that runs after the bucket lookup *is* length-correct, so
only the hash over-reads and the functional behaviour is unaffected — which is
exactly why it has gone unnoticed.

The primitive is a heap out-of-bounds read of at most 7 bytes. The result only
selects a hash bucket — it is not returned to the client and drives no
allocation size or control flow, so there is no infoleak. Without KASAN it does
not even fault, since `kmalloc-8` is the minimum bucket and the read stays
inside the slab object.

## Trigger

1. Any NFSv4 client (this is the server side — the attacker is a client, and no
   special privilege is needed beyond being able to mount).
2. Client sends `EXCHANGE_ID` (v4.1+) or `SETCLIENTID` (v4.0) with a
   `co_ownerid` of 1–7 bytes.
3. `alloc_client()` stores it as a tight `kmemdup(data, len)`.
4. `clientstr_hashval()` is reached during client-record reclaim handling —
   `nfsd4_client_record_check()` → `nfsd4_cld_check{,_v2}()` →
   `nfsd4_find_reclaim_client()`, and from `nfs4_client_to_reclaim()` /
   `inc_reclaim_complete()` — reading 8 bytes from the short object.
5. With KASAN enabled, a slab-out-of-bounds read is reported.

The `nfs4_client_to_reclaim()` call site (`nfs4state.c:8865`) is also reachable
from the nfsdcld `Cld_GraceStart` downcall:
`__cld_pipe_inprogress_downcall()` applies the same validation as the wire
decoder (it rejects only `namelen == 0` and `namelen > 1024`), so a 1–7 byte
name reaches the same `kmemdup` + `clientstr_hashval()` pair.

Reachability is remote, from any NFSv4 client that can reach the server. It
requires nfsdcld client tracking (the default) and a reclaim/grace-period code
path. `CONFIG_NFSD=y`, `CONFIG_NFSD_V4=y` and `CONFIG_SUNRPC=y` must be set for
the code to be built at all; `CONFIG_KASAN_GENERIC=y` is needed to observe the
over-read.
