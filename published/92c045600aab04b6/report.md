# net/tipc: divide-by-zero in `tipc_link_set_queue_limits()` from an unclamped device MTU truncated into the `u16` `tipc_link.mtu`

|  |  |
|---|---|
| Bug class | Divide by zero (kernel Oops / DoS), caused by integer truncation |
| Subsystem | net/tipc |
| Location | `net/tipc/link.c:2531` (`tipc_link_set_queue_limits()`), reached from `tipc_link_create()` |

## Root cause

TIPC validates a bearer's MTU with a **floor and no ceiling**:

```c
/* net/tipc/bearer.h:258 */
static inline bool tipc_mtu_bad(struct net_device *dev)
{
	if (dev->mtu >= TIPC_MIN_BEARER_MTU)
		return false;
	netdev_warn(dev, "MTU too low for tipc bearer\n");
	return true;
}
```

`TIPC_MIN_BEARER_MTU` is `MAX_H_SIZE + INT_H_SIZE == 60 + 40 == 100` (`net/tipc/bearer.h:64`,
`net/tipc/msg.h:97,99`). Any MTU at or above 100 is accepted, and the bearer stores it at full width:

```c
/* net/tipc/bearer.c:467 (enable) and :718 (NETDEV_CHANGEMTU) */
	b->mtu = dev->mtu;          /* u32 <- unsigned int, no min()/clamp */
```

`struct tipc_bearer.mtu` is `u32`. When a link is created, that `u32` is passed through
`tipc_link_create(..., u32 mtu, ...)` and assigned into a field that is only **16 bits wide**:

```c
/* net/tipc/link.c:167-169 */
	/* Max packet negotiation */
	u16 mtu;
	u16 advertised_mtu;
```

So `dev->mtu == 65536` clears the floor as a `u32` (65536 >= 100) and then truncates to
`l->mtu == 0`. `tipc_link_create()` immediately calls `tipc_link_set_queue_limits()`, which divides by
a quantity derived from it:

```c
/* net/tipc/link.c:2529-2531 */
void tipc_link_set_queue_limits(struct tipc_link *l, u32 min_win, u32 max_win)
{
	int max_bulk = TIPC_MAX_PUBL / (l->mtu / ITEM_SIZE);
```

`ITEM_SIZE` is `sizeof(struct distr_item)`, five `__be32` fields, i.e. **20**
(`net/tipc/name_distr.h:42,62-68`). With `l->mtu == 0` the inner division gives `0 / 20 == 0`, and the
outer division is `TIPC_MAX_PUBL / 0 == 65535 / 0` — a **divide error exception in softirq context**.

The two assumptions that disagree: `tipc_mtu_bad()` and `b->mtu = dev->mtu` treat the MTU as an
unbounded `u32`, while `struct tipc_link.mtu` and `tipc_link_set_queue_limits()` assume it fits in a
`u16` and is non-zero once divided by `ITEM_SIZE`. There is no `min()`, `clamp()`, or `U16_MAX` check
anywhere between `dev->mtu` and the `u16 l->mtu`.

The bad values are not limited to 65536: any MTU whose low 16 bits are less than `ITEM_SIZE` triggers
it, i.e. `65536..65555`, `131072..131091`, ... up to `0x7FFF0000`, all of which are accepted on a
device with `max_mtu == 0`.

Secondary effect of the same truncation: `tipc_link_mss()` (`net/tipc/link.c:426`) returns
`l->mtu - INT_H_SIZE - EMSG_OVERHEAD`, which underflows for a tiny `l->mtu` and is later handed to
`tipc_msg_build(..., int pktmax, ...)` as a negative packet maximum.

Note that the netlink route (`net/tipc/bearer.c:1166`, `TIPC_NLA_PROP_MTU`, and the analogous media
path at `:1361`) is *not* unbounded: `tipc_nl_prop_policy` validates `TIPC_NLA_PROP_MTU` with
`NLA_POLICY_FULL_RANGE(NLA_U32, &tipc_nl_mtu_range)` and `tipc_nl_mtu_range.max == U16_MAX`
(`net/tipc/netlink.c:116-125`), so `b->mtu` from netlink can never exceed 65535. Only the **device**
MTU path (`b->mtu = dev->mtu` at `bearer.c:467` and `:718`) is unclamped. The peer-driven path
(`l->mtu = msg_max` at `net/tipc/link.c:2266-2267`) is also floored — `net/tipc/link.c:2219-2220`
rejects the message with `if (msg_max < tipc_bearer_min_mtu(l->net, l->bearer_id)) break;` — so this
bug is local-only; there is no remote variant.

## Trigger

Requires `CONFIG_TIPC` (a module is fine — it autoloads on first `AF_TIPC` socket creation or `tipc`
netlink use). The truncating value has to come from a device MTU, so the bearer must sit on a device
whose `max_mtu` permits an MTU above `U16_MAX`: `dummy` (`drivers/net/dummy.c:126`, `min_mtu = 0;
max_mtu = 0`) and `ifb` (`drivers/net/ifb.c:333-334`) allow anything, and `dev_validate_mtu()`
(`net/core/dev.c:9909`) only enforces `max_mtu` when it is non-zero. `veth` and other ethernet-class
devices cap `max_mtu` at `ETH_MAX_MTU` (65535), and `lo` defaults to mtu 65536 but
`tipc_enable_l2_media()` explicitly refuses `net->loopback_dev` (`bearer.c:441`).

`TIPC_NL_BEARER_ENABLE` carries `GENL_UNS_ADMIN_PERM` (`net/tipc/netlink.c:163-166`), which means
`CAP_NET_ADMIN` in the **user namespace owning the netns**. TIPC is fully namespaced (`tipc_net` is
per-netns, `.netnsok = true`), so an ordinary unprivileged local user who runs
`unshare(CLONE_NEWUSER|CLONE_NEWNET)` obtains that capability against the namespace it owns — no real
privilege is required.

The attacker controls:

1. A device with `max_mtu == 0` (e.g. `dummy`) set to `mtu 65536`, plus a local delivery path on top
   of it (`CONFIG_MACVLAN`), and a TIPC bearer enabled on the carrier device. `tipc_mtu_bad()` passes
   (65536 >= 100) and `b->mtu = 65536` (`net/tipc/bearer.c:467`).
2. A peer discovery frame reaching the node. On receipt, `tipc_disc_rcv()` →
   `tipc_node_check_dest()` → `tipc_link_create(..., b->mtu, ...)` (`net/tipc/node.c:1284-1285`)
   truncates `65536` to `l->mtu == 0` and calls `tipc_link_set_queue_limits()`, which executes
   `65535 / 0`.

An alternative that does not need a peer discovery frame, once a link exists: `tipc link set ... window
N` → `__tipc_nl_node_set_link()` → `tipc_link_set_queue_limits(link, ...)`
(`net/tipc/node.c:2500-2502`) divides using whatever `l->mtu` currently holds.

Result: `divide error: 0000 [#1] SMP` in softirq context — an immediate kernel Oops, and a panic on
`panic_on_oops=1`. The attacker controls only *whether* the fault happens, not any address or value:
this is a local DoS, not a memory-safety issue (no OOB, no UAF, no controlled write, no info leak).
