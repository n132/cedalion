# ALSA: 6fire: unsigned underflow of a device-reported iso length in usb6fire_pcm_in_urb_handler()

|  |  |
|---|---|
| Bug class | Integer underflow → slab out-of-bounds write |
| Subsystem | `sound/usb/6fire` |
| Location | `sound/usb/6fire/pcm.c`:328-338 (`usb6fire_pcm_in_urb_handler()`) |

## Root cause

The capture ("IN") completion handler derives the paired playback ("OUT") URB's
per-packet transfer lengths from the *device-reported*
`iso_frame_desc[].actual_length`, scaled between two different channel
geometries, and then uses the result as a memory-write length without clamping
it against the OUT buffer's own size.

`usb6fire_pcm_in_urb_handler()` does

```c
out_urb->packets[i].length = (in_urb->packets[i].actual_length - 4) / (rt->in_n_analog << 2)
                             * (rt->out_n_analog << 2) + 4;
```

with no clamp against `rt->out_packet_size` / `PCM_MAX_PACKET_SIZE`, and
additionally without the `actual_length > 4` precondition that the sibling
function in the *same file* (`usb6fire_pcm_capture()`, line 209-214) does apply
to the identical expression. That asymmetry is the tell: the author knew the
subtraction needs a guard, and the guard is missing on this path.

`struct usb_iso_packet_descriptor::actual_length` is `unsigned int`,
`in_n_analog == IN_N_CHANNELS == 4` and `out_n_analog == OUT_N_CHANNELS == 6`
(`sound/usb/6fire/pcm.c:18`, set at line 110-111). For any IN packet the device
completes with `status == 0` and `actual_length < 4` — a zero-length
isochronous IN packet being the trivial case — the subtraction wraps:

```
actual_length = 0   ->  0u - 4        = 0xFFFFFFFC
                        / 16          = 0x0FFFFFFF
                        * 24 (mod 2^32) = 0x7FFFFFE8
                        + 4           = 0x7FFFFFEC   (~2.1e9)
```

That value is stored in `out_urb->packets[i].length`, accumulated into the
`int total_length`, and immediately passed to
`memset(out_urb->buffer, 0, total_length)`. `out_urb->buffer` is a
`kcalloc(PCM_MAX_PACKET_SIZE=604, PCM_N_PACKETS_PER_URB=8)` = **4832-byte**
slab object (`usb6fire_pcm_buffers_init()`, line 559-563). The memset therefore
runs ~2 GiB past a kmalloc-8192 object.

If the machine survives that (or if only some packets underflow so that
`total_length` stays small while an individual `packets[i].length` is huge),
the very next steps make it worse rather than better:
`usb6fire_pcm_playback()` (line 262-280) loops
`frame_count = (out_urb->packets[i].length - 4) / (out_n_analog << 2)` and
`memcpy()`s **user-supplied PCM data from `alsa_rt->dma_area`** into `dest` for
that many frames, and the 0x40-stuffing loop at line 356-370 does the same
walk. So the primitive is not only a huge zero-fill but a controlled-content
linear heap overwrite.

There is no clamp of `packets[i].length` to `rt->out_packet_size` or
`PCM_MAX_PACKET_SIZE`, no clamp of `total_length` to
`PCM_N_PACKETS_PER_URB * PCM_MAX_PACKET_SIZE`, and no `actual_length >= 4`
precondition anywhere on this path. The status loop at line 302-306 only
rejects packets with a non-zero `status`; a short/zero-length packet has
`status == 0` and passes. `usb_submit_urb()`'s per-packet length validation
(`drivers/usb/core/urb.c`) would reject the descriptors — but only at line 383,
*after* the `memset()` and the playback `memcpy()`s have already run.

The same expression is also mildly over-optimistic even without underflow: at
rate index 2/3 (`in_packet_size = 420`) a full IN packet yields
`(420-4)/16*24+4 = 628` bytes per packet, `8*628 = 5024 > 4832`; that one is
absorbed by the kmalloc-8192 bucket, so the underflow path is the decisive one.

## Trigger

1. Attacker connects (or emulates, via a USB gadget, USB/IP, or a virtualised
   USB controller) a device with idVendor/idProduct matching the TerraTec DMX
   6Fire USB (`0x0ccd/0x0080`), so `snd_usb_6fire` binds. No user interaction
   beyond plugging in is required on a system with the module available
   (`usb:v0CCDp0080` modalias autoload).
2. The device answers the firmware/comm handshake far enough for
   `usb6fire_pcm_init()` to run and the PCM device to be created.
3. Any local process (a desktop session's audio server, or the attacker on a
   kiosk/locked screen — the ALSA device node is enough) opens the capture
   stream and starts it, which submits the IN URBs
   (`usb6fire_pcm_stream_start()`, line 152-188).
4. The emulated device completes one isochronous IN URB in which any of the 8
   packets carries `actual_length < 4` with `status == 0` (a zero-length packet
   is the simplest and is entirely legal on the bus).
5. `usb6fire_pcm_in_urb_handler()` runs in interrupt context, computes
   `length = 0x7FFFFFEC`, and `memset()`s ~2 GiB starting at a 4832-byte slab
   object.

Note the handler runs even when no PCM substream is active (`sub->active` gates
only the capture/playback copy loops, not the descriptor-setup loop or the
`memset`), so step 3 only needs the *capture* stream started.

**Privilege required**: none in the kernel sense — no capability is needed, and
no `capable()` / `ns_capable()` check exists on the path
(`usb6fire_pcm_prepare` → `usb6fire_pcm_set_rate` → `usb6fire_pcm_stream_start`
→ `usb_submit_urb` → `usb6fire_pcm_in_urb_handler`). The attacker needs control
of an attached USB device (physical access / BadUSB / USB-over-IP / emulated
device) plus a local process able to open the ALSA PCM node (typically the
`audio` group or a desktop session). The malicious length comes from the
device, so the attacker is whoever controls the (possibly emulated) peripheral.

**Configuration**: the code is built only with `CONFIG_SND_USB_6FIRE`, which is
`=m` in Debian/Ubuntu/Fedora stock kernels and autoloads on the
`usb:v0CCDp0080` modalias.
