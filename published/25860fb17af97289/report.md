# libceph: uninitialised slab read in handle_command_ack()

|  |  |
|---|---|
| Bug class | Info leak (uninitialised kernel memory disclosure) / bounds check against the wrong extent |
| Subsystem | net/ceph |
| Location | `net/ceph/mon_client.c:946` (`handle_command_ack()`) |

## Root cause

`handle_command_ack()` bounds its decode against the size of the buffer that
was *allocated* rather than the number of bytes the peer actually *sent*:

```c
/* net/ceph/mon_client.c:946 */
void *p = msg->front.iov_base;
void *const end = p + msg->front_alloc_len;   /* <-- allocation size, not received length */
```

`front_alloc_len` is the size of the buffer that was *allocated*;
`front.iov_len` is the number of bytes the peer actually *sent* (the messenger
sets it from `hdr.front_len`). For MON_COMMAND_ACK these are not the same
number, because the reply message is **preallocated at a fixed 512 bytes** and
reused:

```c
/* net/ceph/mon_client.c:991 — do_mon_command_vargs() */
req->reply = ceph_msg_new(CEPH_MSG_MON_COMMAND_ACK, 512, GFP_NOIO, true);
```

and `mon_alloc_msg()` routes `CEPH_MSG_MON_COMMAND_ACK` to
`get_generic_reply()`, which hands back that preallocated 512-byte message
rather than allocating one sized to the wire. (The
`front_len > m->front_alloc_len` fallback at line 1539 only covers the
*over*-sized case; a peer sending **less** than 512 bytes keeps the 512-byte
buffer with `front.iov_len < 512`.)

So a malicious monitor sends a MON_COMMAND_ACK whose `hdr.front_len` is exactly
`sizeof(struct ceph_mon_request_header)` — i.e. the header and **no result
field at all**. The guard

```c
ceph_decode_need(&p, end, sizeof(struct ceph_mon_request_header) +
					    sizeof(u32), bad);
```

is evaluated against `end = p + 512` and passes comfortably, even though only
the header bytes were received. `p` is advanced past the header and

```c
req->result = ceph_decode_32(&p);
```

reads 4 bytes that were **never written by the peer and never initialised by
the kernel** — `ceph_msg_new()` allocates the front with `kvmalloc()`, not a
zeroing variant, so these are whatever the slab allocator last left there.
The bound is computed from `front_alloc_len` alone, so even a
MON_COMMAND_ACK whose `hdr.front_len` is **zero** — a message with no payload
bytes at all — passes the guard and the kernel still hands back 4 bytes of that
buffer.

The handler as upstream has it:

```c
/* net/ceph/mon_client.c:941-970 — handle_command_ack() */
static void handle_command_ack(struct ceph_mon_client *monc,
			       struct ceph_msg *msg)
{
	struct ceph_mon_generic_request *req;
	void *p = msg->front.iov_base;
	void *const end = p + msg->front_alloc_len;   /* BUG: allocation size, not iov_len */
	u64 tid = le64_to_cpu(msg->hdr.tid);

	dout("%s msg %p tid %llu\n", __func__, msg, tid);

	ceph_decode_need(&p, end, sizeof(struct ceph_mon_request_header) +
							    sizeof(u32), bad);
	p += sizeof(struct ceph_mon_request_header);

	mutex_lock(&monc->mutex);
	req = lookup_generic_request(&monc->generic_request_tree, tid);
	if (!req) {
		mutex_unlock(&monc->mutex);
		return;
	}

	req->result = ceph_decode_32(&p);   /* reads uninitialised slab bytes */
	__finish_generic_request(req);
	mutex_unlock(&monc->mutex);

	complete_generic_request(req);
	return;

bad:
	pr_err("corrupt mon_command ack, tid %llu\n", tid);
	ceph_msg_dump(msg);
}
```

This is an isolated outlier. Every other reply handler in the same file bounds
itself correctly against the received length:

| handler | bound used |
|---|---|
| `handle_subscribe_ack()` (:390) | `if (msg->front.iov_len < sizeof(*h))` ✔ |
| `handle_statfs_reply()` (:749) | `if (msg->front.iov_len != sizeof(*reply))` ✔ |
| `handle_get_version_reply()` (:824) | `end = p + msg->front.iov_len` ✔ |
| `handle_auth_reply()` (:1322) | passes `msg->front.iov_len` as the input length ✔ |
| **`handle_command_ack()` (:946)** | **`end = p + msg->front_alloc_len`** ✘ |

(Note the other `front_alloc_len` uses in this file — `__send_subscribe()` at
:338, `__ceph_monc_get_version()` at :882, and the output-buffer argument at
:1325 — are all *encode* or *output-capacity* paths, where the allocation size
is the correct quantity. Line 946 is the only decode-side use.)

The consequence is a 4-byte read of **uninitialised kernel slab memory**,
within the 512-byte allocation. It is therefore **not** an out-of-bounds
access — KASAN will not fire; KMSAN would. The value lands in `req->result`,
which `do_mon_command_vargs()` returns to its caller and which propagates
upward as an error code. The disclosure channel is consequently narrow (a
4-byte value observed only as an errno, and typically only the low bits are
distinguishable), and the second effect — a mon command reporting a fabricated
success or failure — is a correctness/logic hazard on the blocklist path rather
than a memory-safety one.

## Trigger

1. The client issues any mon command — e.g. `ceph_monc_blocklist_add()`, which
   is called from `fs/ceph` on session teardown/recovery and from the RBD path.
   `do_mon_command_vargs()` allocates `req->reply` as a fixed **512-byte**
   `CEPH_MSG_MON_COMMAND_ACK` message and sends the `CEPH_MSG_MON_COMMAND`.
2. The malicious or compromised monitor replies with
   `CEPH_MSG_MON_COMMAND_ACK` carrying the matching `hdr.tid` and
   `hdr.front_len = sizeof(struct ceph_mon_request_header)` — the header only,
   with the trailing `result` u32 omitted.
3. `mon_alloc_msg()` → `get_generic_reply()` returns the preallocated 512-byte
   message. The messenger reads the short front into it and sets
   `msg->front.iov_len` to the peer's `front_len`; `front_alloc_len` stays 512.
4. `handle_command_ack()` computes `end = p + 512`. The `ceph_decode_need()`
   for `sizeof(header) + 4` passes.
5. `req->result = ceph_decode_32(&p);` reads 4 bytes of uninitialised
   `kvmalloc()`'d slab memory.
6. `__finish_generic_request()` / `complete_generic_request()` wake the waiter,
   and `do_mon_command_vargs()` returns `req->result` — the uninitialised
   value — to its caller.

`mon_alloc_msg()` dispatches `CEPH_MSG_MON_COMMAND_ACK` to
`get_generic_reply()` by **tid only**, not by request type, so any pending
generic request (statfs, `MMonGetVersion`, or a real mon command) is a valid
target. Generic requests are issued by the client on its own during normal
operation — `ceph_wait_for_latest_osdmap()` → `ceph_monc_get_version(monc,
"osdmap")`, `ceph_statfs()` → `ceph_monc_do_statfs()`.

**Reachability**: remote, from a malicious or compromised **monitor**. Path:
`mon_dispatch()` → `handle_command_ack()`, on the reply to any mon command the
client issues.

**Privilege required**: **none on the client.** No local account and no
capability on the client is needed; the attacker only has to be — or to have
compromised — the monitor the client is already configured to talk to. The
value reaches userspace: on the RBD path `req->result` propagates through
`ceph_monc_get_version()` → `ceph_wait_for_latest_osdmap()`
(`net/ceph/ceph_common.c:863`) → `rbd_get_client()`, which prints it with
`rbd_warn(NULL, "failed to get latest osdmap: %d", ret)` and returns it from
`write(2)` on `/sys/bus/rbd/add_single_major`.

**CONFIG**: `CONFIG_CEPH_LIB` plus a libceph consumer (`CONFIG_BLK_DEV_RBD` or
`CONFIG_CEPH_FS`).

**Affected**: present at `a500db7819c50db59e55f1b4fa1c3baa5a2616f3`
(`v7.3-rc1-250-ga500db7819c5`).
