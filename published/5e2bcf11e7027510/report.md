# can: peak_usb: slab out-of-bounds read in `pcan_usb_handle_bus_evt()`

|  |  |
|---|---|
| Bug class | Slab out-of-bounds read (info leak) |
| Subsystem | drivers/net/can/usb/peak_usb |
| Location | `drivers/net/can/usb/peak_usb/pcan_usb.c`:553 (`pcan_usb_handle_bus_evt()`) |

## Root cause

`pcan_usb_decode_status()` establishes exactly a **two-byte** bound and then consumes both bytes:

```c
/* drivers/net/can/usb/peak_usb/pcan_usb.c:586 */
	/* check whether function and number can be read */
	if ((mc->ptr + 2) > mc->end)
		return -EINVAL;

	f = mc->ptr[PCAN_USB_CMD_FUNC];		/* [0] */
	n = mc->ptr[PCAN_USB_CMD_NUM];		/* [1] */
	mc->ptr += PCAN_USB_CMD_ARGS;		/* += 2 — mc->ptr may now equal mc->end */
```

After this advance **nothing** is known to be in bounds. Every other arm of the following switch
respects that: `PCAN_USB_REC_ANALOG` and `PCAN_USB_REC_BUSLOAD` set `rec_len` and rely on the
trailing `if ((mc->ptr + rec_len) > mc->end) return -EINVAL;`, `pcan_usb_decode_ts()` checks
`ptr+1`/`ptr+2` itself, and `pcan_usb_decode_error()` touches no payload.

`PCAN_USB_REC_BUSEVT` is the one arm that does not:

```c
	case PCAN_USB_REC_BUSEVT:
		/* bus event notifications (get rxerr/txerr) */
		err = pcan_usb_handle_bus_evt(mc, n);
```

and the handler reads at `[1]` and `[2]` from the already-advanced cursor — i.e. up to **three bytes
past `mc->end`**:

```c
/* drivers/net/can/usb/peak_usb/pcan_usb.c:553 — reads [1] and [2] with nothing validated */
static int pcan_usb_handle_bus_evt(struct pcan_usb_msg_context *mc, u8 ir)
{
	struct pcan_usb *pdev = mc->pdev;

	/* according to the content of the packet */
	switch (ir) {
	case PCAN_USB_ERR_CNT_DEC:
	case PCAN_USB_ERR_CNT_INC:

		/* save rx/tx error counters from in the device context */
		pdev->bec.rxerr = mc->ptr[1];
		pdev->bec.txerr = mc->ptr[2];
		break;
	...
	}

	return 0;
}
```

The trailing `(mc->ptr + rec_len) > mc->end` check runs only **after** the switch, and for a BUSEVT
record the attacker sets `rec_len = status_len & PCAN_USB_STATUSLEN_DLC` to 0, so even that
post-hoc check passes cleanly. (Note also that the function's own comment says "first byte contains
rxerr while 2nd one contains txerr" while the code reads indices 1 and 2 — the reads are off by one
relative to the documented layout, which is likely how the missing bound went unnoticed.)

`mc->end` is `ibuf + urb->actual_length` and the RX buffer is
`kmalloc(dev->adapter->rx_buffer_size)` with `PCAN_USB_RX_BUFFER_SIZE == 64` — an exact kmalloc-64
bucket. A device that reports `actual_length = 64` and lays out its records so that the final status
record's two argument bytes end exactly at offset 64 causes `ibuf[65]` and `ibuf[66]` to be read:
a KASAN-visible slab-out-of-bounds read whose two bytes are stored into `pdev->bec.rxerr` /
`pdev->bec.txerr` and subsequently reported to userspace by `pcan_usb_get_berr_counter()` via
`do_get_berr_counter` (`ip -details -statistics link show canX`, or the CAN netlink
`IFLA_CAN_BERR_COUNTER` attribute).

**Secondary, same file**: `pcan_usb_decode_msg()` drives its loop off the device-supplied record
count with no cursor bound at the loop head —

```c
/* drivers/net/can/usb/peak_usb/pcan_usb.c:736 */
	struct pcan_usb_msg_context mc = {
		.rec_cnt = ibuf[1],			/* device-supplied, never validated */
		.ptr = ibuf + PCAN_USB_MSG_HEADER_LEN,
		.end = ibuf + lbuf,
	};
	for (err = 0; mc.rec_idx < mc.rec_cnt && !err; mc.rec_idx++) {
		u8 sl = *mc.ptr++;			/* no `mc.ptr < mc.end` test */
```

— giving a 1-byte overread at `mc.end` when `rec_cnt` exceeds the records actually present. It is a
real but distinct missing bound in the same function.

**Why it is NOT already fixed**: the bounds discipline in this file was clearly retrofitted into the
*sub-decoders* — `pcan_usb_decode_ts()`, `pcan_usb_decode_status()`'s trailing check and
`pcan_usb_decode_data()` all carry explicit `(mc->ptr + N) > mc->end` guards — but
`pcan_usb_handle_bus_evt()` and the driving loop head were left outside it, and `rec_cnt` is never
related to `lbuf` anywhere in the file.

The resulting primitive is a 2–3 byte info leak of memory adjacent to a kmalloc-64 object, laundered
into the CAN berr counters and readable by any unprivileged process via netlink; plus a 1-byte
overread from the loop head. The leak is only two bytes per transfer, but it is repeatable at will
(one URB per leak) and the attacker controls which offset is read by padding the record layout, so
it can be iterated to scan adjacent slab memory a couple of bytes at a time. It is not a corruption
primitive.

## Trigger

1. Attacker attaches a USB device (physical, USB/IP, or `dummy_hcd`/`raw-gadget`) advertising a
   PCAN-USB VID/PID (`0x0c72` / `0x000c`) so `peak_usb` binds with `pcan_usb_adapter`, and brings the
   CAN interface up.
2. The device completes the bulk-IN transfer with `actual_length = 64` (the full `kmalloc(64)`
   buffer). It lays out records — e.g. a mix of `default:`-function status records (3 bytes each)
   and `PCAN_USB_REC_BUSLOAD` records (4 bytes each) — so that the final record's two argument bytes
   end exactly at offset 64.
3. That final record is a status record (`PCAN_USB_STATUSLEN_INTERNAL` set) with
   `status_len & PCAN_USB_STATUSLEN_DLC == 0`, no timestamp bit, `f = PCAN_USB_REC_BUSEVT` and
   `n = PCAN_USB_ERR_CNT_DEC`.
4. `pcan_usb_decode_status()` passes its `ptr + 2 > end` gate, advances `ptr` to `end`, and
   `pcan_usb_handle_bus_evt()` reads `ibuf[65]` and `ibuf[66]` into `pdev->bec`.
5. Any unprivileged process reads the leaked bytes back with
   `ip -details -statistics link show canX` (or a `RTM_GETLINK` netlink dump), which surfaces the
   CAN bus error counters.

The overread runs in the URB completion handler, in softirq context, from the device's own data. No
`capable()` / `ns_capable()` gate stands between the URB completion and the buggy read, and reading
the counters back requires no privilege at all. The attacker supplies the peripheral and holds no
account or capability on the victim.

**Configuration**: the defect needs nothing but `CONFIG_CAN_PEAK_USB` (with `CONFIG_CAN`,
`CONFIG_CAN_DEV`) and a device claiming VID `0x0c72` / PID `0x000c`. Only the *observation* of the
overread needs `CONFIG_KASAN`; on a production kernel the same code silently copies the two adjacent
slab bytes into `pdev->bec` and hands them to userspace through `IFLA_CAN_BERR_COUNTER`.
