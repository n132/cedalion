# udlfb: slab use-after-free in dlfb_setup_modes()

|  |  |
|---|---|
| Bug class | slab-use-after-free (read) |
| Subsystem | drivers/video/fbdev (udlfb) |
| Location | `drivers/video/fbdev/udlfb.c`:1267 (`dlfb_setup_modes()`) |

## Root cause

The core establishes the correct idiom in `do_unregister_framebuffer()`:

```c
/* drivers/video/fbdev/core/fbmem.c:547-548 */
	fbcon_delete_modelist(&fb_info->modelist);	/* un-publish: clear every fb_display[i].mode */
	fb_destroy_modelist(&fb_info->modelist);	/* only then kfree the elements */
```

`fbcon_delete_modelist()` is precisely the "tell the holders the memory is going away" step:

```c
/* drivers/video/fbdev/core/fbcon.c:2758-2775 */
static void fbcon_delete_mode(struct fb_videomode *m)
{
	struct fbcon_display *p;

	for (int i = first_fb_vc; i <= last_fb_vc; i++) {
		p = &fb_display[i];
		if (p->mode == m)
			p->mode = NULL;
	}
}

void fbcon_delete_modelist(struct list_head *head)
{
	struct fb_modelist *modelist;

	list_for_each_entry(modelist, head, list)
		fbcon_delete_mode(&modelist->mode);
}
```

`dlfb_setup_modes()` performs the destroy **without** the un-publish:

```c
/* drivers/video/fbdev/udlfb.c:1267-1268 */
	fb_destroy_modelist(&info->modelist);		/* no fbcon_delete_modelist() first */
	memset(&info->monspecs, 0, sizeof(info->monspecs));
```

At probe time (`udlfb.c:1684`) this is harmless — it runs *before* `register_framebuffer()` at line 1701,
so no console can hold a pointer yet. But `dlfb_setup_modes()` is also reachable **after** registration,
from the `edid` sysfs binary attribute:

```c
/* drivers/video/fbdev/udlfb.c:1442-1467 */
static ssize_t edid_store(struct file *filp, struct kobject *kobj,
			  const struct bin_attribute *a,
			  char *src, loff_t src_off, size_t src_size) {
	struct device *fbdev = kobj_to_dev(kobj);
	struct fb_info *fb_info = dev_get_drvdata(fbdev);
	struct dlfb_data *dlfb = fb_info->par;
	int ret;

	if ((src_size != EDID_LENGTH) || (src_off != 0))
		return -EINVAL;

	ret = dlfb_setup_modes(dlfb, fb_info, src, src_size);	/* frees the live modelist */
	...
	ret = dlfb_ops_set_par(fb_info);
	...
}

/* drivers/video/fbdev/udlfb.c:1484-1490 */
static const struct bin_attribute edid_attr = {
	.attr.name = "edid",
	.attr.mode = 0666,		/* world-writable */
	.size = EDID_LENGTH,
	.read = edid_show,
	.write = edid_store
};
```

When fbcon is bound to the udlfb framebuffer, `var_to_display()` has set
`fb_display[i].mode = fb_match_mode(var, &info->modelist)` — a pointer to the `struct fb_videomode`
embedded in a heap `struct fb_modelist` element. `edid_store()` then `kfree()`s every one of those
elements while `fb_display[i].mode` still points into them, and nothing clears the pointers:

- `fb_destroy_modelist()` is a plain `list_del` + `kfree(pos)` loop — no RCU grace period, no notifier.
- `dlfb_ops_set_par()`, the only thing `edid_store()` calls afterwards, does **not** call
  `fbcon_update_vcs()`, `fbcon_new_modelist()`, `var_to_display()` or anything else that would
  re-point `fb_display[i].mode`. It only compares/sets `info->var`, reallocates the shadow buffer,
  programs the hardware and repaints.
- The rebuilt list is populated with fresh `fb_add_videomode()` allocations, so even an identical mode
  is a *different* object — the old pointer is not accidentally revalidated.

The dangling `fb_display[i].mode` is then consumed by ordinary console activity:
`fbcon_switch()` → `display_to_var()` → `fb_videomode_to_var(var, disp->mode)` reads `mode->xres`,
`mode->yres`, the margins and the timings out of freed memory and programs them into the video mode;
`fbcon_new_modelist()` passes it to `fb_find_nearest_mode()`; `fbcon_mode_deleted()` feeds it to
`fb_mode_is_equal()`. Note `fbcon_new_modelist()`'s `if (!fb_display[i].mode) continue;` guard does not
help — the pointer is dangling, not NULL, which is exactly why the missing `fbcon_delete_modelist()`
matters.

The primitive is a use-after-free **read** of a freed `struct fb_modelist` slab object, where the read
values (`xres`, `yres`, margins, `pixclock`, `sync`, `vmode`) are subsequently used to program a
video mode and to size console geometry. If the freed slab is reallocated with attacker-controlled
bytes, this yields controlled input into mode setting and `vc_resize()` — potentially escalating
beyond a pure info leak.

**Secondary defect on the same line.** `memset(&info->monspecs, 0, sizeof(info->monspecs))` at
`udlfb.c:1268` discards `info->monspecs.modedb` without calling `fb_destroy_modedb()` first. Every
`edid_store()` after the first therefore leaks the previous EDID mode database (allocated by
`fb_edid_to_monspecs()`); only the final one is freed in `dlfb_ops_destroy()`. Because the attribute is
`0666`, an unprivileged user can loop on it to exhaust kernel memory. Reported here rather than
separately since it is the same statement pair and the same fix hunk.

## Trigger

Requires a DisplayLink USB device bound to `udlfb` (`CONFIG_FB_UDL`), with fbcon bound to that
framebuffer so that `fb_display[i].mode` is populated.

1. Attach a DisplayLink USB display; `udlfb` probes and calls `register_framebuffer()`, creating
   `/sys/class/graphics/fbN/` including the `0666` `edid` attribute.
2. Ensure fbcon is using this framebuffer (it will be if it is the console fb; otherwise map a VT to it
   via `con2fbmap`). `var_to_display()` sets `fb_display[i].mode` to point into `info->modelist`.
3. As **any unprivileged user**, write a 128-byte EDID blob at offset 0 to
   `/sys/class/graphics/fbN/edid`. The blob must parse — `fb_edid_to_monspecs()` must yield
   `modedb_len > 0` — and must match what `dlfb_get_edid()` reads back, or `edid_store()` returns
   `-EINVAL` *after* the free has already happened (the free is not undone on the error path, so even
   the rejected case leaves the dangling pointers).
4. `dlfb_setup_modes()` runs `fb_destroy_modelist(&info->modelist)`, freeing every element that
   `fb_display[i].mode` points into. No `fbcon_delete_modelist()` runs, so the pointers survive.
5. Trigger console activity that dereferences the stale pointer — switch VTs (`chvt`), resize the
   console, or change the video mode — reaching `fbcon_switch()` → `display_to_var()` →
   `fb_videomode_to_var(var, disp->mode)`.
6. Under KASAN this reports `slab-use-after-free` in `fb_videomode_to_var()`. Spraying the freed slab
   between steps 4 and 5 lets the attacker control the timing values that are then read and pushed into
   the hardware mode-setting path.

Note step 3's error path: because `edid_store()` returns `-EINVAL` when the readback does not match but
`dlfb_setup_modes()` has already destroyed the list, an attacker does not even need a well-formed EDID
that the hardware will echo back — any parseable blob is enough to strand the pointers.

**Privilege required**: **none** — `edid_attr.attr.mode` is `0666`, world-writable, and there is no
`capable()` / `ns_capable()` check anywhere on the `edid_store()` → `dlfb_setup_modes()` →
`fb_destroy_modelist()` path. A DisplayLink device is USB, so an attacker with physical access can
supply one and `udlfb` binds automatically. The free is deterministic and requires no race, and the
window before the stale pointer is used is unbounded and attacker-controlled — the attacker chooses
when to switch VTs.
