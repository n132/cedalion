# media: em28xx-alsa: divide by zero in `em28xx_audio_urb_init()`

|  |  |
|---|---|
| Bug class | Divide by zero (kernel oops at device enumeration) |
| Subsystem | `drivers/media/usb/em28xx` |
| Location | `drivers/media/usb/em28xx/em28xx-audio.c`:718 (`em28xx_audio_urb_init()`) |

## Root cause

A degenerate descriptor value (`wMaxPacketSize == 0`) flows into size arithmetic
that assumes it is non-zero: the descriptor field is used as a *divisor* without
being reconciled with anything at all.

The USB core does **not** reject a zero `wMaxPacketSize`. `usb_parse_endpoint()` in
`drivers/usb/core/config.c` clamps only *upward*:

```c
/* drivers/usb/core/config.c:448-486 — the core only warns about maxp == 0 */
	maxp = le16_to_cpu(endpoint->desc.wMaxPacketSize);

	if (maxp == 0 && bcdUSB != 0x0220 &&
	    !(usb_endpoint_xfer_isoc(d) && asnum == 0))
		dev_notice(ddev, "config %d interface %d altsetting %d endpoint 0x%X has invalid wMaxPacketSize 0\n",
		    cfgno, inum, asnum, d->bEndpointAddress);
	...
	if (maxp > j) {
		... maxp = j;
		endpoint->desc.wMaxPacketSize = cpu_to_le16(i | maxp);
	}
```

— a `dev_notice()` and nothing more. `usb_submit_urb()` *does* reject `maxp == 0`, but that check is
never reached here because the oops happens during setup, before any URB is submitted.

`em28xx_audio_urb_init()` locates the audio endpoint by address and direction only:

```c
/* drivers/media/usb/em28xx/em28xx-audio.c:679-696 — no size or type check on the endpoint */
	for (i = 0; i < intf->altsetting[alt].desc.bNumEndpoints; i++) {
		e = &intf->altsetting[alt].endpoint[i].desc;
		if (!usb_endpoint_dir_in(e))
			continue;
		if (e->bEndpointAddress == EM28XX_EP_AUDIO) {
			ep = e;
			break;
		}
	}

	if (!ep) {
		dev_err(&dev->intf->dev, "Couldn't find an audio endpoint");
		return -ENODEV;
	}

	ep_size = em28xx_audio_ep_packet_size(udev, ep);
	interval = 1 << (ep->bInterval - 1);
```

There is no size check and no transfer-type check on the matched endpoint.
`em28xx_audio_ep_packet_size()` returns `(size & 0x7ff) * (1 + ((size >> 11) & 0x03))` at high speed, or
`size & 0x7ff` otherwise — **zero if the device declares `wMaxPacketSize = 0`** (or, at high speed, if
the low 11 bits are zero regardless of the multiplier bits):

```c
/* drivers/media/usb/em28xx/em28xx-audio.c:645-655 — returns 0 for wMaxPacketSize 0 */
static int em28xx_audio_ep_packet_size(struct usb_device *udev,
				       struct usb_endpoint_descriptor *e)
{
	int size = le16_to_cpu(e->wMaxPacketSize);

	if (udev->speed == USB_SPEED_HIGH)
		return (size & 0x7ff) *  (1 + (((size) >> 11) & 0x03));

	return size & 0x7ff;
}
```

`ep_size` is then used twice as a divisor:

```c
/* drivers/media/usb/em28xx/em28xx-audio.c:710-737 — the divisions */
	bytes_per_transfer = DIV_ROUND_UP(48000 * 2 * 2, 125 * interval);
	...
	num_urb = DIV_ROUND_UP(bytes_per_transfer, ep_size);     /* <-- divide by zero */
	if (num_urb > EM28XX_MAX_AUDIO_BUFS)
		num_urb = EM28XX_MAX_AUDIO_BUFS;
	...
	urb_size = bytes_per_transfer / num_urb;
	...
	npackets = EM28XX_MIN_AUDIO_PACKETS;
	if (urb_size > ep_size * npackets)
		npackets = DIV_ROUND_UP(urb_size, ep_size);          /* <-- and again */
```

`DIV_ROUND_UP(n, 0)` expands to `(n + 0 - 1) / 0` — an integer division by zero, i.e. `#DE` and a kernel
oops on x86 (and an undefined-result trap or silent garbage on other architectures).

**Why this is not already fixed.** Every sibling driver in the same subsystem carries the guard that
em28xx lacks:

- `drivers/media/usb/uvc/uvc_video.c` floors the bandwidth calculation at 1 and, on the bulk path,
  explicitly returns `-EIO` when `maxp == 0`;
- `drivers/media/usb/cx231xx/cx231xx-core.c` guards with `alt > 0 && max_pkt_size == 0`.

em28xx's video and DVB paths are also fine (they multiply by `max_pkt_size` rather than dividing by it);
it is only this audio path that divides.

Consequence: a divide-by-zero oops. On most configurations this kills the probe thread; with
`panic_on_oops` set it panics the machine, and even without it the kernel is left with a dead
workqueue/probe context. No memory corruption, no information disclosure — DoS only.

## Trigger

1. Present a USB device matching one of the em28xx device IDs, via `CONFIG_USB_RAW_GADGET` +
   `dummy_hcd` or any programmable gadget. No physical Empia hardware required.
2. Declare the interface layout em28xx expects, and in the altsetting the audio path selects
   (altsetting 1 when `dev->ifnum != 0`, otherwise altsetting 7) include an **IN** endpoint whose
   `bEndpointAddress` equals `EM28XX_EP_AUDIO` and whose **`wMaxPacketSize` is 0**.
3. Ensure the card is treated as having vendor audio so that `em28xx_audio_init()` runs (the
   `has_vendor_audio` decision in `em28xx-cards.c` keys off the endpoint being isochronous, not off its
   size).
4. Plug the device in / bind the gadget. Probe reaches `em28xx_audio_urb_init()`, computes
   `ep_size = 0`, and executes `DIV_ROUND_UP(bytes_per_transfer, 0)` at `em28xx-audio.c:718` → divide
   error, kernel oops in probe context.

This runs at **enumeration**, from `em28xx_audio_init()` (registered as the extension's `.init`), so no
userspace action, no `open(2)` and no permission on any device node is required — plugging the device
in is sufficient.

**Reachability.** Pure enumeration. Plugging in (or emulating) a device with the right IDs and a
zero-`wMaxPacketSize` audio endpoint is sufficient — no device node needs to be opened and no
userspace process needs to cooperate. There is no `capable()`/`ns_capable()` on the path from
descriptor parse to the divide. On a desktop with USB auto-probing this is a physical-access
attack; with `USB_RAW_GADGET` + `dummy_hcd` it is reachable from a local process with access to
`/dev/raw-gadget`. Distributions build `em28xx` and `em28xx-alsa` as modules, auto-loaded by the USB
modalias for `usb:v0EB1Ap2820*`.

**Required CONFIG.** `CONFIG_VIDEO_EM28XX` and `CONFIG_VIDEO_EM28XX_ALSA` — the latter builds
`em28xx-audio.c`, the file containing the divide.
