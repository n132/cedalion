# nvmet-rdma: out-of-bounds read in nvmet_rdma_parse_cm_connect_req()

|  |  |
|---|---|
| Bug class | slab out-of-bounds read |
| Subsystem | drivers/nvme/target (nvmet-rdma) |
| Location | `drivers/nvme/target/rdma.c:1409` (`nvmet_rdma_parse_cm_connect_req()`) |

## Root cause

Audited at mainline commit `238650ef6c7c7cca08e032527329424c9fbd70e5`
(`v7.3-rc3-82-g238650ef6c7c`).

`nvmet_rdma_parse_cm_connect_req()` casts RDMA-CM private data to a 32-byte
`struct nvme_rdma_cm_req`, but validates only that the pointer is non-NULL and
the length is nonzero. It then reads `recfmt`, `qid`, `hsqsize`, and `hrqsize`
without requiring `private_data_len >= sizeof(*req)` or even enough bytes for
the fields actually consumed.

```c
static int
nvmet_rdma_parse_cm_connect_req(struct rdma_conn_param *conn,
				struct nvmet_rdma_queue *queue)
{
	struct nvme_rdma_cm_req *req;

	req = (struct nvme_rdma_cm_req *)conn->private_data;
	if (!req || conn->private_data_len == 0)
		return NVME_RDMA_CM_INVALID_LEN;

	if (le16_to_cpu(req->recfmt) != NVME_RDMA_CM_FMT_1_0)
		return NVME_RDMA_CM_INVALID_RECFMT;

	queue->host_qid = le16_to_cpu(req->qid);
	queue->recv_queue_size = le16_to_cpu(req->hsqsize) + 1;
	queue->send_queue_size = le16_to_cpu(req->hrqsize);

	if (!queue->host_qid && queue->recv_queue_size > NVME_AQ_DEPTH)
		return NVME_RDMA_CM_INVALID_HSQSIZE;

	return 0;
}
```

The fixed-size IB-CM private-data area masks this problem on InfiniBand, but it
does not establish the invariant for iWARP. The iWARP CM core preserves the
provider/peer length and copies exactly that many bytes with
`kmemdup(event->private_data, event->private_data_len, ...)`; CMA forwards the
same `private_data_len` to nvmet-rdma.

```c
p = kmemdup(event->private_data, event->private_data_len, GFP_ATOMIC);
/* ... */
event.param.conn.private_data = iw_event->private_data;
event.param.conn.private_data_len = iw_event->private_data_len;
```

A six-byte request can provide valid `recfmt`, `qid`, and `hrqsize`, while the
read of the two-byte `hsqsize` at offsets 6–7 crosses the logical allocation
boundary. With KASAN this is a remote report/crash. Without KASAN, stale bytes
in the kmalloc object's tail become `recv_queue_size`; if queue allocation
succeeds, `nvmet_rdma_cm_accept()` returns that value as `priv.crqsize`,
exposing the stale 16-bit value to the initiator. The current parser has no
full-length check.

The primitive is an out-of-bounds read of up to the connection-request fields
consumed by the parser. A six-byte request exposes a stale 16-bit heap-tail
value through the accepted connection's `crqsize`; malformed derived queue
sizes can also drive large allocations and denial of service.

## Trigger

The fault is reached remotely and pre-authentication through an exposed
NVMe/RDMA iWARP listener. It occurs while handling
`RDMA_CM_EVENT_CONNECT_REQUEST`, before an NVMe Fabrics Connect command or
subsystem host authorization. No privilege is required on the target or
initiator beyond network access to the iWARP listener.

The code is compiled only when `CONFIG_NVME_TARGET_RDMA` is enabled; reaching
it over software iWARP additionally requires `CONFIG_INFINIBAND` and
`CONFIG_RDMA_SIW`. `CONFIG_KASAN` turns the read into an immediate report but
is not required to trigger it.

1. Expose an NVMe/RDMA target through an iWARP provider (for example software
   iWARP/siw) and listen on the configured RDMA-CM endpoint.
2. From userspace on a remote iWARP-capable host, issue an RDMA-CM connection
   request with six bytes of private data rather than the required 32-byte
   `struct nvme_rdma_cm_req`.
3. Encode `recfmt = NVME_RDMA_CM_FMT_1_0`, a nonzero `qid`, and a small
   `hrqsize` in those six bytes. Leave `hsqsize` absent.
4. IWCM `kmemdup()` allocates/copies exactly six bytes and CMA reports
   `private_data_len == 6`.
5. `nvmet_rdma_parse_cm_connect_req()` passes its nonzero-length check and
   reads `req->hsqsize` from bytes 6–7 beyond the copied object.
6. KASAN reports the OOB read, or a non-KASAN kernel uses the stale two-byte
   value for allocations and may echo it (plus one) in the CM response's
   `crqsize`.
